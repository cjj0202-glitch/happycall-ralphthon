# 고객 요청 근거화의 독립 검토

2026-09-21 · pc1 CJJ · `/root/fixed_recheck_semantics` · 제품 읽기 전용.

FIX-W05에서 고객이 하지 않은 단위 확인 요청을 제거하고 실제 주문·라벨 요청을 보존한 것은 확인했습니다. 저장 36응답의 재처리 결과와 자동 필드도 기존 귀속 보완 결과를 유지했습니다. 그러나 독립 9반례는 5통과·4실패이며, 향후 부탁 의향과 취소된 요청을 현재 요청으로 채택하는 P1 두 건이 남아 일반 요청 귀속 인수는 보류 의견입니다.

## P1: 향후 부탁 의향을 현재 고객 요청으로 채택

원문: `다음 주에 라벨을 확인해 주세요라고 부탁하려고 합니다.`

모델이 고른 인용: `라벨을 확인해 주세요`

기대 request: null과 원문 대조 안내. 실제 request: `라벨을 확인해 주세요`.

이는 내일 확인해 달라는 현재 요청이 아니라, 다음 주에 부탁하려는 의향을 설명한 문장입니다. `server/request_grounding.py`의 NON_CURRENT는 예정·계획 등의 표현은 잡지만 `부탁하려고 합니다`를 통과시킵니다. 인용 앞뒤를 읽었어도 현재 요청 여부 판정에 실패합니다. 독립 R04로 재현했습니다.

## P1: 바로 뒤에서 취소한 요청을 계속 유지

원문: `라벨을 확인해 주세요. 그 요청은 취소합니다.`

모델이 고른 인용: `라벨을 확인해 주세요.`

기대 request: null과 현재 요청 재확인. 실제 request: `라벨을 확인해 주세요.`.

`current_request_quote`는 마침표로 끝난 인용 뒤에 따옴표·인용 조사 등이 없으면 뒤 문장을 읽지 않습니다. 동일 경영주 발화에서 요청을 취소한 문장이 있어도 철회 전 행동을 접수에 남깁니다. 이미 취소된 요청으로 업무가 이관될 수 있어 P1입니다. 독립 R05로 재현했습니다.

## P2: 정상 명사형 요청 소실 및 잘린 동작 인용 채택

| 반례 | 원문 | 인용 | 기대 | 실측 |
|---|---|---|---|---|
| R02 | 반송 방법 안내 요청입니다. | 원문 전체 | 명시 요청 보존 | request=null |
| R06 | 라벨을 확인해 주세요. | 주세요. | 동작 없는 조각은 자동 request로 채택하지 않음 | request=주세요. |

텍스트 접수에서 흔한 목적격 없는 명사형 요청은 현재 REQUEST 패턴의 문법에 없어 소실됩니다. 반대로 동작과 대상이 없는 종결어미 조각은 패턴에 맞아 유효한 요청으로 들어갑니다. 전체 문장에서 동작·대상을 복원할 권한이 없는 이 계약에서는 원문 대조 안내로 남기는 것이 안전합니다.

## 실제 문제 해결과 저장 원응답 재처리

새 4호출의 FIX-W05 이전 자유 request는 주문·라벨 확인에 고객이 하지 않은 단위 확인 요청을 덧붙였습니다. 새 결과는 검증된 실제 인용 `출고 운영에서 주문과 라벨을 확인해 주세요.`와 정확히 일치합니다. unit=null은 이번 범위에서 채우지 않고 AI 추가 확인을 질문에만 둡니다. 원래 허위 요청 추가 P1은 이 저장 응답에서 해소됐습니다.

새 EDGE-12는 고객 요청을 바꾸지 않고 수량·단위를 함께 원문 대조하도록 AI 질문을 추가했습니다. 과거 BOX를 오늘 필드에 옮기지 않아 기존 질문 누락 보완도 확인했습니다.

| 대조 | 이전 32응답 | 새 4응답 |
|---|---:|---:|
| 직접 normalize_analysis 재처리 | 32 | 4 |
| 사전 oracle 자동 4필드 | 128/128 | 15/16 |
| request와 선택된 인용 일치 | 31/32 | 4/4 |
| 인용 불일치로 request=null | EDGE-09 1건 | 0건 |
| 구현자 after와 독립 최종 결과 일치 | 32/32 | 4/4 |
| 직전 귀속 보완 결과 대비 자동 필드 변경 | 0 | 0 |
| summary/subject/department/facts/issues/unknowns 변경 | 0 | 0 |

31/32와 4/4는 인용 보존 개수입니다. 요청이 충분한지, 현재 요청인지, 빠진 조건이 없는지의 의미 정답률이 아닙니다. EDGE-09의 합성된 인용은 그대로 null이며 실제 고객 요청이 없다는 판정이 아닙니다. 새 FIX-W05의 단위 null 오답 1셀도 그대로 남았습니다. 36개 관측은 서로 다른 합성 입력 36개가 아니라 32건과 그중 4건을 다시 호출한 결과입니다.

## 실행 명령과 실측

```powershell
.venv/Scripts/python.exe -B -X utf8 .local/request-grounding-independent/probe.py
.venv/Scripts/python.exe -B -X utf8 -m pytest -q tests/test_request_grounding.py tests/test_analysis_repair.py tests/test_analysis_semantics.py tests/test_analysis_grounding_regression.py -rs
```

첫 명령의 출력:

```text
R01 true, R02 false, R03 true, R04 false, R05 false,
R06 false, R07 true, R08 true, R09 true
reprocessed=36, sourcesPreserved=44, codeUnchanged=true
```

두 번째 명령: `95 passed, 166 subtests passed in 5.26s`, 종료 코드 0. 기존 테스트가 통과해도 새 독립 네 실패가 사라지는 것은 아닙니다. 독립 스크립트의 종료 코드 0은 결과 저장과 불변성 assertion 성공이며 `probes[].pass`가 실제 판정입니다.

제품·원문·expected·기존 결과·원장은 편집하지 않았습니다. 원래 두 run의 44파일 해시와 검토 코드 3파일 해시가 실행 전후 일치했습니다. 직접 재처리는 SDK·키 진입을 AssertionError로 막고 수행했으며 새 API·과금 호출은 0건입니다.

## 인수 범위와 제한

FIX-W05 허위 단위 요청 제거, 원문 요청 보존 방식, AI 질문 분리, 명시 미래시각·금지 요청 보존, 정확히 같은 질문 중복 방지는 확인한 입력 범위에서 인정할 수 있습니다. 그러나 향후 의향·철회 문장을 현재 요청으로 채택하는 두 P1을 같은 정상/반례 조건으로 보완하기 전에는 일반 고객 요청 귀속 안전 인수를 권하지 않습니다.

선택된 인용 바깥의 불만·조건 누락은 이 코드가 복구하지 않습니다. 이번 검토는 통제한 원응답 재처리와 제한된 독립 반례이며 라이브 모델 재평가·음성/STT·사람 사용성·배포·모든 한국어 요청 의미를 검증하지 않았습니다. 소유 밖 제품 파일 변경, 유료 호출, 커밋, 발송은 하지 않았습니다.
