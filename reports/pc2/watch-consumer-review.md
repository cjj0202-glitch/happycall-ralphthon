# N02-O1 — 감시 소비자별 스냅샷 분리 검토

작성: 2026-09-22 01:18 KST, pc2 안영일 / GitHub MR-A83.

상주 감시가 먼저 읽은 회신을 다른 소비자가 놓치는 현상을 임시 디렉터리에서 재현했고, `watch --consumer NAME`으로 탐지 상태를 분리했습니다. 수정 후 두 소비자가 댓글 0→1 변화를 각각 회신 1건으로 탐지합니다. 실제 운영 소비자 이름 적용과 최종 인수는 pc1 검토 후 진행합니다.

## 사용 계약

| 호출 | 상태 파일 | 의미 |
|---|---|---|
| `watch` 또는 `watch --once` | `.mailbox_state.<실제 슬롯>.json` | 기존 경로 그대로. 미지정 호출끼리는 공유합니다. |
| `watch --consumer main-loop --once` | `.mailbox_state.<실제 슬롯>.main-loop.json` | 이름이 다른 소비자와 별도 기준점을 유지합니다. |

소비자 이름은 소문자 영문으로 시작하는 1~32자 ASCII 소문자·숫자·밑줄·하이픈으로 제한합니다. 대문자 별칭, 경로 구분자, 점, 상위 경로, 드라이브 표기, 공백, 비ASCII, 과도한 길이를 거절합니다. `_state_path`도 재검증합니다. `--consumer pc4`는 pc2에서 `.mailbox_state.pc2.pc4.json`을 뜻하며 pc4의 신원이나 수신함으로 바꾸지 않습니다.

등록 확인 `me()`, GitHub 인증, 실제 슬롯의 `to:pc2`/`from:pc2` 조회, 변화 계산, 오류 시 마지막 정상 상태 보존과 backoff는 기존 경로를 유지합니다. 예전 호출 객체에 `consumer` 속성이 없어도 기존 동작을 지원합니다. 새 상태 파일은 기존 `.gitignore` 43행의 `.mailbox_state.*.json`에 포함되므로 ignore 규칙 변경이 필요 없습니다.

새 소비자는 빈 기준점으로 시작하므로 첫 조회에서 기존 열린 편지도 알립니다. 같은 소비자 이름의 동시 실행은 계속 같은 파일을 공유하므로 해당 경쟁은 해결하지 않습니다. 이는 소비자별 변화 탐지이며 큐·claim·처리 완료·ACK 저장소가 아닙니다. 무출력은 미처리 결과가 없다는 증거가 아닙니다. 이 한계를 CLI 도움말과 상주 감시 시작 안내에도 넣었습니다.

## 기대값과 실제 검증

실제 GitHub 응답 대신 메모리 응답과 임시 디렉터리를 사용했습니다. 새 실제 댓글을 테스트용으로 만들거나 운영 스냅샷을 수정·삭제하지 않았습니다.

| 검사 | 기대 / 실제 |
|---|---|
| 수정 전 재현 | A와 B 기준 댓글 0 설정 후 댓글 1. A는 회신 1건, B는 0건으로 독립 탐지 기대를 위반. 기존 공유 경로에서 재현했습니다. |
| 수정 후 독립 탐지 | A가 먼저 읽어도 B도 회신 1건. 각각 다시 조회하면 정확히 무출력. 서로 다른 임시 상태 파일 모두 댓글 1 보존. |

| 네트워크 실패 | 이름 있는 소비자의 마지막 정상 파일 바이트 유지, 3·6초 backoff 기대 일치(시간 대기는 모의 처리). |
| 변이 | 같은 독립 탐지 오라클의 CONTROL 통과 후, 메모리에서 소비자 분리만 제거한 변이는 B 탐지 누락 `AssertionError`로 검출. 원래 함수 복원. |
| 관련 전체 검사 | `python -B -m unittest discover -s tests -p test_mail_watch.py -v`: 기존 8 + 신규 15 = **23/23 PASS**, 0.205초, 실패·SKIP 0. 변이는 이 23개에 포함하며 별도 중복 합산하지 않습니다. |

## 운영 적용 제안과 한계

pc1이 코드를 검토·통합한 후 메인 루프의 소비자 이름을 명시하는 호출 예시입니다.

```powershell
python -B channel/mail.py watch --once --consumer main-loop
```

이름 없는 기존 상주 감시는 기존 경로를 그대로 쓰고, 이름을 붙인 메인 루프는 별도 경로를 씁니다. 다른 독립 소비자에는 다른 이름을 고정해서 사용합니다. 이 작업에서 실제 호출을 적용하거나 상주 감시를 재시작하지 않았습니다.

기존 pc2 상주 감시 PID `27156`, 생성 시각 `2026-09-21T17:05:46.389001+09:00`, 명령의 `channel/mail.py watch --interval 30`을 작업 전후 대조했으며 동일 프로세스를 유지했습니다. 운영 스냅샷은 원래 상주 감시가 정상 갱신하므로 파일이 영구 불변이라고 주장하지 않습니다. 감시기·launcher·자동화·공용 지침·보안 설정·브라우저·서버 변경은 없습니다.

소비자가 다르더라도 현재 스냅샷 기반 탐지의 기존 보존·조회 한계는 유지됩니다. 실제 GitHub 전달, 사람이 읽었는지, 작업 처리 여부, TEST 성공을 입증한 검사가 아닙니다. pc1의 실제 소비자 설정과 인수가 남아 있습니다.

앞선 N02-M5 도구는 main `37de103`에 신규 8파일 범위로 인수된 것을 확인했습니다. 공식 WAV는 여전히 0/2, 공식 타임라인은 0/20으로 미검증이며, O1의 통과가 음원·부모 UI·사람 청취·N02 전체 인수·TEST의 완료를 뜻하지 않습니다.
