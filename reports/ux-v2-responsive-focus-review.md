# UX v2 반응형·키보드 포커스 검증

2026-09-22 00:27~00:32 KST · pc1/CJJ · 기준 HEAD `535febe1a9cccf351deeab82a8a843b0e891149b`

기존 IAB의 OneFlow 탭에서 390×844, 768×1024, 1280×900의 **실제 innerWidth/innerHeight**를 확인했습니다. 모바일 역방향 키보드 탐색 중 입력란과 질문 버튼이 sticky 메뉴 뒤에 가리는 결함을 재현해 CSS만 수정했습니다. 수정 후 같은 24회 키보드 이동과 업무 앵커 21회가 통과했습니다. 사람 사용성 관찰·전체 기능 승인·최종 배포 완료를 뜻하지 않습니다.

## First Bolt: 실패 → 수정 → 같은 조건 재시험

- 사례: 상담원 작업대 / CASE-0002 / 390×844 / 저장된 기존 분석 화면.
- 재현: `2 접수 대조·편집` 링크 클릭 → Tab 12회 → Shift+Tab 12회. 필드 편집·확인 체크·저장·API 분석은 실행하지 않았습니다.
- 판정: 활성 요소의 top이 고정 메뉴 bottom(98px) 이상이며 화면 안에 보여야 합니다.

| 역방향 순서 | 요소 | 수정 전 top / bottom | 수정 후 top / bottom | 메뉴 bottom |
|---|---|---:|---:|---:|
| 4 | 추가 질문 메모 | 32.617 / 87.805 | 242.617 / 297.805 | 98 |
| 5 | 추가 확인 질문 버튼 | 0.117 / 57.117 | 153.617 / 210.617 | 98 |

기존 순방향 12개는 보였으나 역방향 12개 중 2개가 완전히 가렸습니다. 수정 후 순방향 12/12·역방향 12/12가 보였습니다. 접수 편집 앵커 top은 수정 전후 모두 144.046875px로 유지됐습니다.

수정은 `apps/web/app/globals.css` 한 곳입니다. 앵커별 scroll-margin을 0으로 바꾸고 문서 scroll-padding에 같은 토큰 기반 여백(데스크톱 96px, 768px 이하 144px)을 둡니다. 두 여백이 합산되지 않으며, 입력란에 대한 브라우저 자동 스크롤에도 안전 영역이 적용됩니다. 실제 레이아웃 padding·높이·내부 스크롤은 바꾸지 않습니다.

## 업무 흐름 앵커 7개 × 실제 폭 3개

각 링크를 UI에서 클릭한 뒤 activeElement가 해당 영역인지, top이 메뉴 아래인지, 문서 가로 넘침이 없는지 읽었습니다. 페이지 하단에 가까운 앵커는 최대 스크롤에 도달하므로 보정값보다 아래에 위치할 수 있습니다.

| 실제 폭 × 높이 | 문서 clientWidth / scrollWidth | 메뉴 bottom | 상담 4개 top: 원문 / 접수 / 근거 / 전달 | 센터 3개 top: 근거 / 조치 / 회신 |
|---|---:|---:|---|---|
| 390×844 | 375 / 375 | 98 | 144 / 144.047 / 143.992 / 434.414 | 144 / 158.469 / 290.969 |
| 768×1024 | 753 / 753 | 98 | 144 / 144 / 143.945 / 648.633 | 144 / 370.281 / 502.781 |
| 1280×900 | 1265 / 1265 | 54 | 96 / 96 / 96.156 / 535.844 | 96 / 289.781 / 397.781 |

- 21/21 앵커의 포커스 대상이 맞고 메뉴 아래에 위치했습니다. 6개 역할·폭 조합 모두 scrollWidth=clientWidth였습니다.
- 센터 `새 이관 0건`은 실제 빈 화면으로 확인했습니다. `전체 접수 보기`로 CASE-0002의 이관 전 열람 화면을 열었습니다. 회신 작성 UI 검증이며 실제 회신 저장/종결 성공 증거는 아닙니다.
- 1280px 상담 작업대와 768px 센터 회신 화면을 스크린샷으로 확인했습니다.
- 수집된 warn/error 콘솔 로그는 0건입니다. 과거 모든 로그가 없다는 뜻이 아닙니다.
- 경영주 화면으로 돌아가 기존 미저장 합성 문의 문장 전체가 유지된 것을 DOM에서 대조했습니다. 기존 접수 결과 확인 대기 상태를 유지했으며 재시도하지 않았습니다.
- 임시 viewport override는 reset하고 상담원 화면을 남겼습니다. 새 탭·서버·브라우저 실행, 새로고침, 상태 초기화는 하지 않았습니다.

## 독립 검토와 검사 한계

독립 explorer가 실제 diff·전체 CSS·앵커 7곳을 읽어 여백 상쇄 누락이 없는지 확인했습니다. 내부 overflow 영역에는 scroll-padding이 상속되지 않습니다. 경영주/WMS/TMS의 문서 자동 스크롤에도 여유가 생기는 범위 확대는 있으나 레이아웃 공간을 추가하지 않습니다. 위 브라우저 수치는 메인 실측이며 별도의 독립 브라우저 실행으로 세지 않습니다.

조직 토큰 검사 `node C:/00.프로젝트/75_하네스_클라우드배포/01_프론트엔드/01_토큰/check.mjs`는 CSS 46파일/hex 272건, JS·HTML 230파일/hex 3119건을 스캔했고 **E601 기준선 3029→3119 증가로 실패**했습니다(명령 exit 1, 검사 문구는 exit 2). 실제 소비처는 50/91/scmops이며 해피콜은 포함되지 않습니다. 이 결과를 해피콜 통과로 사용하지 않습니다. 이번 diff에는 색·폰트·새 치수 리터럴이 없고 기존 control-xl 토큰만 사용합니다. 조직 기준선이나 다른 프로젝트를 변경하지 않았습니다.

`git diff --check` 통과. CSS 수정만 있으므로 이미 통과한 상태 전이·저장 로직 테스트를 반복하지 않았습니다. 생산 빌드/배포 묶음은 이번 변경을 아직 포함하지 않습니다. 렌더 진행 중 사용 가능 메모리 1,335,296,000 bytes가 기존 빌드 문턱 1.5GiB보다 낮아 새 빌드는 시작하지 않았습니다. 추후 최종 통합 빌드에 포함해야 합니다.
