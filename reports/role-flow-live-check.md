# 역할별 실제 화면 흐름 점검

## 실행 전 계획

2026-09-21 23:00 KST 이후, pc1의 기존 IAB tab6와 기존 3100/8100 서비스를 사용합니다. 기준 역할 UI는 `bcbbb35`, 메인 HEAD는 `7d186fd`입니다. 기존 문의를 초기화하지 않고 합성 웹 문의를 새로 만들어 검사합니다. 실제 고객·물류 시스템·외부 푸시는 대상이 아닙니다. 분석 방식은 replay이며 유료 AI 호출은 하지 않습니다.

두 입력은 미도착(가상 한빛점, 당일1회차 전체 미수령)과 오출고(가상 새봄점, 비스킷 주문 대신 휴지1BOX 수령)입니다. 각 1회 웹접수→상담 원문/정제 대조→근거 조사→확인·이관→센터 조치→최종 회신→경영주 조회를 실행합니다. 고정 release의 음성 포함6회 재검증을 대신하지 않습니다.

검사할 기대값:

1. 생성된 접수 ID가 역할 이동·WMS/TMS 조사·복귀·회신 조회에서 일치한다.
2. 필수 대조·사람 확인 전 이관이 차단되고, 확정 뒤 센터의 새 이관 목록으로 이동한다.
3. 센터에서는 상담 접수 내용을 변경하지 않으며, 남은 조치가 있으면 최종 회신·종결이 차단된다.
4. 중간 회신과 최종 회신의 상태·문구가 경영주 조회와 일치한다.
5. 오류가 나오면 성공으로 보고하지 않고 입력·화면·원인·수정 후 재시험을 기록한다.

## 실제 결과와 중단 지점

첫 미도착 입력에서 기존 CASE-0001을 명시 선택하여 SYN-ST01·당일1회차 전체를 채우고 합성 문의를 보냈습니다. 화면은 즉시 저장 여부 미확정을 표시했습니다. `접수 저장 여부 확인` 뒤 404에 해당하는 미등록 안내와 같은 내용 재시도 버튼을 표시했고, 입력은 유지됐습니다. 재시도는 하지 않았습니다. 신규 접수 성공0건, 전체 흐름 완료0/2이며 오출고는 미실행입니다.

동일 실행 API 8100에 읽기 전용 조회와 OPTIONS 대조를 했습니다:

| 요청 | 상태·실측 |
|---|---|
| GET /api/cases | 200, 22건(시작과 동일) |
| POST preflight, content-type/x-demo-role/x-idempotency-key | 400 `Disallowed CORS headers` |
| 같은 preflight에서 기존 content-type/x-demo-role만 지정 | 200 `OK` |

Origin은 모두 `http://127.0.0.1:3100`이며 응답의 허용 헤더는 `Accept, Accept-Language, Content-Language, Content-Type, X-Demo-Role`입니다. 현재 소스 `server/app.py`에는 `X-Idempotency-Key`가 포함되어 있지만 실제 PID17112 런타임에는 반영되지 않았습니다. 단순히 모든 API가 중단됐거나 목록이 비었다는 결론이 아닙니다. 브라우저의 POST가 preflight 단계에서 차단된 것이며 응답 미확정·저장 확인 UI는 동작했습니다.

이전 자동 승인 검토가 기존 API 재시작을 거절했으므로 재시작·새 서버·프록시·헤더 제거로 우회하지 않았습니다. 외부 상태나 권한 변화 증거 없이 같은 동작을 재시도하지 않습니다. 기존 서버·브라우저·입력 초안·22개 접수는 보존했습니다. 최신 코드의 서버 없는 ASGI 검사와 이 실행 API의 실제 브라우저 결과를 구분합니다.

현재 소스의 `.venv/Scripts/python.exe -X utf8 -m pytest tests/test_intake_idempotency.py::test_http_create_retry_recovery_and_cors -q`는 1 passed(2.66초, 의존성 deprecation 경고5)였습니다. 격리된 저장소와 인프로세스 TestClient로 생성·동일 키 재시도·복구·CORS를 검사한 결과이며 PID17112가 고쳐진 뜻은 아닙니다.
