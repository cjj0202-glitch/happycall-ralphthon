# 실제 음성 분석의 수령 수량 계약 수정

작성일: 2026-09-21 · 작성: pc1 대기세션5 · 대상: CASE-0002 실제 STT·분석 품질

수령 수량을 주문 수량으로 해석한 실제 실패와 프롬프트 수정 후 재실패를 보존했습니다. 현재 2차 수정에서는 주문·수령 진술을 별도로 추출하고 서버가 인용·점포명·원본 근거를 대조해 기존 HTTP 응답을 생성합니다. 실제 모델의 의미 정확도가 개선됐는지는 아직 입증하지 않았습니다.

## 2차 구조 수정

1차 프롬프트 수정 뒤 같은 WAV로 실시한 [실제 재검증](e2e/live-analysis-after.json), requestId `fa902a32-9237-414e-bc6a-f5551cf02881`도 18 EA를 반환했습니다. 단위 오류 설명은 1 BOX 정정을 인용하면서 필드는 주문 수량을 써 내부 모순이 생겼고, 사실 목록에는 서로 다른 점포명이 동일하다는 문장이 생성됐습니다. 두 응답이 같은 WAV 해시라는 사실과 각 응답의 수량·단위 실패를 테스트로 고정했습니다.

2차 수정에서는 `MODEL_ANALYSIS_SCHEMA`를 공개 `ANALYSIS_SCHEMA`와 분리했습니다. 모델은 `orderedClaim`과 `receivedClaim`에 각각 상품·수량·단위·원문 인용을 작성합니다. 내부 `fields`는 문의 대상과 요청만 허용하므로 수량·단위·점포코드를 중복 생성할 수 없습니다. 생성형 facts 필드도 내부 계약에서 제외했습니다.

`normalize_analysis`가 다음을 수행합니다.

- 수령 수량·단위는 `receivedClaim`만 사용합니다. 상품이 없거나 인용이 실제 STT 한 구간에 없으면 두 값을 null로 두고 확인 질문을 추가합니다. 대본·fixture 정답·주문량·출고량으로 보충하지 않습니다.
- 인용은 가장자리 공백만 제거해 대조합니다. 중간 공백·문구를 고치거나 여러 구간을 합쳐 유효한 인용으로 만들지 않습니다.
- 점포코드는 추출 이름과 마스터 이름의 공백 제거 후 정확 일치, STT 인용 존재, 인용 내 이름 존재를 모두 만족해야 채웁니다. 유사 발음은 null과 점포 확인 질문으로 남깁니다.
- facts는 `status=fact`인 원본 행의 식별자·시스템·항목·값·출처를 그대로 표시합니다. 다른 상태의 원본 행과 모델의 미확인 제안은 unknowns에 분리합니다. 모델의 점포 동일성 문장을 사실로 승격하지 않습니다.
- 부서명은 허용된 부서 ID의 정본 이름으로 덮어씁니다. 수량·단위·점포에 대한 모델 진단은 버리고 대조 결과로 작성합니다. 주문·수령 상품이 다르면 문의 대상에도 둘을 구분하고, 요약은 두 진술로 구성합니다.

인용이 실제로 존재한다는 것은 그 문구를 모델이 올바르게 해석했다는 증거가 아닙니다. 예를 들어 실제 “한 박스” 인용에 모델이 `receivedClaim=18 EA`를 붙이면 현재 구조는 그 의미 오류를 자동으로 판별하지 못합니다. 이 경우 수작업 기대값과 비교한 평가기가 계속 실패하도록 한계 테스트를 유지했습니다. 화자 식별·최종 정정 선택·부정 표현·수량 의미의 일반적 정확도를 보장하지 않습니다.

## 1차 프롬프트 수정 기록

- `server/analysis_schema.py`: quantity와 unit에 수령 기준 설명을 추가했습니다. 공용 nullable 문자열 정의는 바꾸지 않았습니다.
- `server/live.py`: 주문·발주·피킹·출고·부족분을 수령 필드에 넣지 않고, 고객의 최종 정정을 후속 상담원 오독으로 덮어쓰지 않도록 지시했습니다.
- 개·낱개는 EA, 박스·상자는 BOX로 표기만 정규화합니다. 박스 입수를 이용해 수량을 환산하지 않습니다. 모르는 값은 null, 해당 상품의 명시적인 수령 0은 0으로 남깁니다.
- 같은 수령 대상끼리 상담 입력을 비교합니다. 수량이 같고 단위만 틀리면 단위 불일치로 진단하고 고객 정정 발화의 문구·순서 또는 시각을 근거로 남깁니다.
- 경영주의 수령 진술을 검증된 인도 사실로 바꾸지 않습니다. 여러 수령 상품 중 문의 대상이 불분명하면 수량·단위를 비우고 확인 질문을 남깁니다.

서비스·예산·UI는 이번 변경 범위에 포함하지 않았습니다. UI에서는 후속 작업으로 수량 라벨을 수령 기준이라고 표시해야 합니다.

## 평가 범위와 반례

`tests/test_analysis_semantics.py`의 기대값은 수작업으로 정한 평가 기준입니다. 평가기가 STT를 해석하거나 실제 모델을 실행하는 것은 아닙니다. 이미 알려진 잘못된 응답을 거부하고, 평가용으로 작성한 올바른 응답을 수용하는지 검사합니다. 자연어 오류 진단·인용의 타당성은 별도 사람 검토 대상입니다.

| 입력 조건 | 기대 수령 필드 | 실패로 볼 결과 |
|---|---|---|
| 주문 18 EA, 수령 1 BOX, 상담 입력 1 EA | 1 / BOX | 18 / EA; 입력 1 대 주문 18을 비교한 수량 오류 주장 |
| 고객이 2박스에서 1박스로 정정한 뒤 상담원이 1개로 오독 | 1 / BOX | 후속 상담원 오독으로 단위 변경 |
| 주문 18 EA만 알고 실제 수령량은 모름 | null / null | 주문·출고 수량으로 보충 |
| 해당 상품 수령 0개를 명시 | 0 / EA | 0을 null로 지움 |
| 주문 2 BOX, 실제 수령 18 EA | 18 / EA | 작은 숫자 또는 BOX를 항상 선택 |
| 수령 2 BOX, 박스당 12개 | 2 / BOX | 24 EA로 자동 환산 |
| 서로 다른 상품 1 BOX와 6 EA, 문의 대상 불명 | null / null 및 확인 질문 | 7로 합산하거나 한 상품을 임의 선택 |

원상담 입력을 1 BOX로 바꾼 대조군에서는 입력 불일치가 없어야 합니다. 서로 다른 상품·단위를 차감하면 안 된다는 일반 경고까지 금지하지는 않습니다. 단순히 `issues.field=quantity`가 존재한다는 이유만으로 실패를 판정하지 않습니다.
