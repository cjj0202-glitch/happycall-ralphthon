# 복수 요청 서버 구현 독립 검토

2026-09-22 새 메인 PC, 구현 담당자와 별도 검토. `server/request_provenance.py`, `request_grounding.py`, `live.py`, `analysis_schema.py`와 신규 검사를 대상으로 했다. 검토자는 제품 파일을 수정하지 않았다. 아래는 실제 합성 입력 실행 결과이며 모델 정확도·브라우저·배포 인수가 아니다.

최종 판정: 발견한 P2 4종과 부정 취소의 추가 문장부호 경계는 수정 후 같은 입력에서 해소됐다. 최종 **PC2 31/31·독립 입력 15/15** 통과, 공개 schema·입력 불변을 확인했다. 동일 문구 반복의 보수적 유보와 일반 한국어 의미 판별의 한계는 남긴다.

## 첫 독립 관측

PC2의 고정 기대값 31행은 활성·거절·이유·출처 범위 전부 일치했다. 별도로 작성한 14개 입력은 6개 통과, 8개 실패했다. 8개 실패는 아래 P2 결함 4종으로 묶인다. 모든 실패를 순수 resolver와 `normalize_analysis`의 공개 `fields.request` 양쪽에서 재현했다.

| 결함 | 독립 입력과 기대 | 수정 전 실측 |
|---|---|---|
| P2: 다른 대상의 요청까지 철회 | 반송 방법/교환 방법 두 요청 뒤 교환 방법만 취소하면 반송은 남아야 한다. 치약 반송/컵 반송 뒤 컵만 취소하는 변형도 같다. | 두 입력 모두 전체 요청이 `WITHDRAWN`, 공개 요청 null |
| P2: 부정된 취소 인용을 실제 철회로 오인 | 반송 요청→상담원 발화→`저는 "반송 방법 요청은 취소합니다"라고 말한 적이 없습니다.`는 반송 요청을 철회하지 않는다. | `WITHDRAWN`, 공개 요청 null |
| P2: 부사 유무로 정정 문맥 검사 우회 | `한 개가 아니라 한 박스예요. 단위를 기록해 주세요.`에서 뒤 문장만 제안되면 정정값이 빠졌으므로 검토해야 한다. | `단위를 기록해 주세요.` 활성, 검토 사유 없음 |
| P2: 익명 STT 라벨을 같은 사람으로 확정 | `화자`/`unknown`/`speaker`/`none` 각 라벨로 요청과 취소가 서로 다른 구간에 있으면 같은 사람이 취소했다고 확정할 수 없다. | 4개 모두 역할 미확인과 동시에 `WITHDRAWN`, 공개 요청 null |

첫 원인은 `_same_target`가 공통어 한 개의 교집합을 같은 대상으로 취급하고 새 철회 경로가 이를 그대로 사용하는 것이다. 두 번째는 후속 취소 문장의 인용·부정 문맥을 검사하지 않는 것이다. 세 번째는 정정 문맥 검사 진입이 `제대로/정확히`에 의존한다. 네 번째는 인접 연결의 `_explicit_speaker`와 달리 철회 경로가 비어 있지 않은 fallback 라벨을 같은 화자로 인정한다. 최초 관측 위치는 `request_provenance.py`의 84·95·115·118행 및 `request_grounding.py`의 84행이다. 이후 수정으로 행 번호가 이동할 수 있다.

양성 대조는 전체 정정 인용 보존, 실제 대상 일치 철회, 다른 화자의 취소 뒤 원요청 보존, 같은 명시 화자의 인접 인용이다. 음성 대조는 중간 구간 생략과 다른 화자 연결의 거절이다. 입력 전후 deep equality, 수령 수량/단위 null 유지, 공개 JSON schema 유효성을 함께 확인했다. `ANALYSIS_SCHEMA`는 고정 `c20d411`의 값과 완전히 같았다.

## 재현과 증거

```powershell

```

실행기는 기대값을 제품 출력으로 계산하지 않는다. 모델·키·원장 접근 지점을 실패 대역으로 막고 합성 분석값만 투영한다. 실행 전후 제품 소스 해시가 같은지 확인한다. 초기 10개 입력의 관측도 `independent-request-review-before.json`에 보존했고, 익명 화자 4개를 추가한 동일 조건의 최종 수정 전 기준은 `independent-request-review-before-v2.json`이다. 재현 코드와 상세 입력·기대·실측·소스 해시는 모두 ignored `.local/main-resume-20260922/` 아래에 있다.

수정 전 `server/request_provenance.py` SHA256은 `03306854489e66775f56389a8e868972c0b1526b15a648d6deb9224c8f44f041`이다. 소유가 다른 파일의 동시 작업이 있으므로 HEAD만으로 작업트리를 고정했다고 주장하지 않는다.

## 합의한 범위와 후속

동일한 현재 요청을 두 번 강조해도 출처가 복수이면 `AMBIGUOUS_OCCURRENCE`로 유보되는 관측이 추가로 있었다. 메인은 이번 범위에서 출처를 임의 선택하지 않는 보수적 정책을 유지하기로 결정했다. 이는 위 4개 결함·14개 입력의 분모에 포함하지 않으며 별도 정책 관측으로 남긴다. 일반적인 반복 요청을 자동 보존한다는 주장을 하지 않는다.

P2 결함은 즉시 메인과 구현 담당자에게 정확한 입력·기대·실측으로 전달했다. 과금·실모델·외부 API·원격 배포·커밋·push는 수행하지 않았다.

## 첫 수정 후 같은 조건 재검과 인용 경계

구현 담당자의 수정 통보 후 같은 실행기의 같은 14개 입력은 **14/14**, PC2 기대값은 **31/31** 통과했다. 공개 schema·입력 불변도 유지했다. 결과는 `independent-request-review-after.json`이며 이 실행에서 resolver SHA256은 `f9020728384bad7fa3d04e864be953b8abda90c1f6e2edc43e734c12bd156800`이었다.

변경 코드의 문장 경계를 추가로 대조하자 같은 부정 취소 결함이 인용 안 마침표 하나에서 재발했다. 후속 발화를 `저는 "반송 방법 요청은 취소합니다."라고 말한 적이 없습니다.`로 바꾸면 `_sentences`가 인용 내부 마침표에서 문맥을 잘라 `라고 말한 적이 없습니다`가 철회 문맥 검사 밖으로 빠졌다. 순수 resolver와 공개 요청 모두 여전히 철회로 처리했다. 별도 입력을 1개 추가한 **15개 분모 중 14개 통과/1개 실패** 결과는 `independent-request-review-after-boundary.json`에 보존했다. 이전 14개 통과 결과를 변경하지 않았다.

이 추가 경계 역시 새 결함군이 아니라 부정 취소 P2의 미완전 수정이며 메인·구현 담당자에게 즉시 전달했다.
