# 전체 솔루션 지도 — 이번 결정과 후속 확장

상태: **이번 범위 DEC-001~015 반영 / B01~B03 전체 인수·4인 의견 미완료**. 이번 범위와 큰 솔루션의 후속 후보를 함께 보존하며 구현 완료나 네 사람의 합의를 뜻하지 않는다. 행사 P0 기준선은 [목표](../docs/03_목표와_범위.md), 상세 계약은 [제품 설계](../docs/04_제품_상세설계.md)를 참고한다.

## 하나의 업무 흐름

주사용자는 점포 문의를 받는 상담 담당자, 센터 담당자는 이관받은 문의를 확인·조치하고 최종 회신하는 책임자입니다. 메인 사용자 결정 [DEC-001](decisions.md)을 반영했으며, 아래 기능 범위 전체에 대한 4인 합의를 뜻하지 않습니다.

경영주 통화/사이트 글 제출 → 통화 종료 후 STT·GPT 또는 텍스트 GPT 정제 → 상담 접수 확인·수정 → 케이스 식별 → 별도 WMS/TMS 근거 조회 → 사실/미확인 분리 → 답변 초안 → 상담원 확인·이관 → 센터 회신·잔여 조치 처리 → 경영주 회신 조회·종결 → 처리 이력 → 후속 반복 문제 개선.

이번 시연은 미도착·오출고 두 유형, 음성·텍스트 두 채널, 경영주 접수/조회·상담 작업대·센터 회신·WMS·TMS 화면을 연결합니다. 실제 STT/GPT는 이번 필수이며 replay는 명시적 대체입니다. WMS/TMS는 현재 demo-v1의 SYN-* 합성 근거로 시연합니다. 다른 문의 유형과 실 운영 연결은 후속 확장으로 보존합니다.

| 영역 | 책임 | 공유 정보 | 행사에서 검증할 부분 | 후속 제품 후보 |
|---|---|---|---|---|
| 접수 | 음성/텍스트에서 문의를 보존하고 필드 수정 | Intake, Utterance, Case ID | 실제 STT/GPT·텍스트 제출·출처·수동 보정 | 실시간 통화 코칭·추가 채널 |
| 케이스 | 문의 상태와 담당 흐름 관리 | Case, version | 두 유형·목록·상세 | SLA·우선순위·담당 분배 |
| 근거 | 원본 행·시각·연결 키 제공 | Evidence, source refs | 주문/WMS/TMS/영상 연결 | 실 시스템 adapter·수집 갱신 |
| 판단 지원 | 사실·추론·미확인·권고 분리 | Decision, unknowns | 실제 GPT 초안·사실/미확인·오류/모순 검토 | 규칙 편집·추가 공급자 |
| 조치 | 사람 확인 후 인계하고 기록 | Action, requestId | 상담 이관·센터 회신·잔여 조치·경영주 조회 | 실 승인·업무 시스템 연계 |
| 미디어 | 관련 자산과 원본 연결 정보 | Media manifest | 합성 음성/영상·실패 대체 | 접근제어·만료·보관 정책 |
| 평가 | 기대값과 실제 결과 비교 | Evaluation, build SHA | 20입력·12경계·반복 시연 | 회귀셋·현장 피드백 |
| 운영/분석 | 권한·관측·개선 지표 | Actor, Audit, metric definitions | 기본 모드/합성 표시·측정 | 권한, 감사, 센터/유형 분석 |

## 확장 순서의 제안

1. **해커톤:** 두 케이스와 두 인입 채널, 실제 전사·정제, 근거·미확인·사람 이관, 센터 회신·조치 종결·경영주 조회가 작동한다. DEC-013의 AI Playwright는 기술 검증이며 사람 관찰·업무효과는 미검증이다.
2. **파일럿:** 업무 담당자 관찰, 동의된 비식별 자료, 실제 입력·조회 연동, 접근 권한과 실패 복구를 검증한다. 일정·비용은 아직 정하지 않았다.
3. **운영 확장:** 처리 승인과 실 시스템 쓰기, SLA·통계, 새로운 문의 유형, 센터 확장. 책임·권한·감사·운영 검증을 별도 설계한다.

큰 솔루션을 하나의 경험과 계약으로 묶되, 배포를 마이크로서비스로 나눌지는 미정이다. 첫 구현에 없는 모듈을 메뉴만 만들어 완료로 표시하지 않는다. 공식 채점은 장기 비전 문서의 양보다 실제 위임·검증·완료 증거에 연결한다.

## 네 사람이 공통으로 결정할 경계

| 함께 결정할 것 | 결정하지 않으면 생기는 충돌 | 정본·확인 시점 |
|---|---|---|
| 문의 한 건의 완료 상태와 주사용자 | 한 화면은 답변 생성, 다른 화면은 실제 처리 완료로 해석 | docs/03, B01 |
| Case ID·점포·시각·원본 참조와 계약 버전 | 다른 케이스 자료가 섞이거나 조회 시점이 지워짐 | docs/04·contracts, P02/B03 |
| `missing/conflicting`와 조회 오류·처리 상태 | 데이터 누락을 시스템 장애 또는 배송 사실로 오해 | docs/04·상태별 fixture, P02 |
| UI 입력·상태·주행동·접근성·공통 컴포넌트 | PC마다 흐름과 완료 의미가 달라짐 | UX01~03 관찰 반영 후 docs/04 |
| 쓰기 소유자·멱등 키·사람 확인·이력 | 중복 처리, 오래된 초안 확정, 담당 불명 | docs/04·API 계약, B03 |
| 모듈 경로·공통 파일 작성자·합치는 순서 | 서로 맞는 코드가 충돌하거나 같은 파일을 덮음 | B03·작업 카드·G02 |
| replay/demo-live·수동 검토와 배포 경계 | 재생 결과를 실제 AI·실제 업무 처리로 발표 | 기술 결정카드·G01·H01/H02 |

각 경계에는 결정 ID와 담당자를 붙인다. 작은 모듈 안의 사소한 구현 선택까지 네 사람 회의로 올리지 않는다. 공통 계약·사용자 결과·수용 기준·일정을 바꾸는 선택만 공유 결정으로 관리한다.

First Bolt는 이 지도 전체를 축소해 한꺼번에 만드는 일이 아니다. Journey에서 선택한 병목 하나를 화면 안의 작은 과업으로 시험하고, 결과가 영향을 주는 영역만 갱신한다. 후보·관찰은 [교육 적용](../docs/16_FDE_First_Bolt_적용.md), 기능 포함·제외는 [기능표](features.md)에 연결한다.
