## 사용자 결과와 실측

상담원이 통화를 마친 뒤 단위 정정·잘못 온 상품 처리·주문 상품 처리 요청을 함께 확인할 수 있어야 합니다. 각 문구는 실제 전사에서 출처를 대조할 수 있어야 하며 철회된 요청이나 AI 추가 질문을 고객 요청으로 만들지 않습니다.

04:11~04:13 실제 현행 WAV→STT→정제에서 CASE2의 실제 STT에는 세 요청이 있었으나 모델의 단일 requestQuote는 비연속 발화를 합쳤고, normalizer의 원문 검증에 의해 최종 request=null이 됐습니다. CASE1/2의 subjectQuote도 여러 STT 구간을 합쳐 현재 단일 구간 검사에 걸렸습니다. 이 가운데 같은 화자의 연속 구간과 다른 화자가 끼어 있는 비연속 구간은 구분해야 합니다. [사전 기준](../reports/evaluation/voice-canary-20260922-oracle.json)을 낮추지 않습니다.

## 계약 방향과 소유

메인은 모델 전용 schema·normalizer·원문 검증 모듈을 소유합니다. PC2는 아래 독립 입력/기대값과 설계 반례만 작성하며 공통 제품 파일을 편집하지 않습니다. 실제 구현 전에 아래 후보를 정상/반례로 검토해 고정합니다.

1. 모델 전용 draftContext는 단일 요청 인용 대신 복수 요청 인용을 표현합니다. 후보는 `requestQuotes: string[]`이며 각 인용은 별도로 검증하고 최대8개로 제한합니다. 같은 요청의 중복과 순서 역전은 전사 위치로 대조합니다. 공개 HTTP의 `fields.request: string|null` 계약은 유지하며 검증된 개별 인용을 구분해 표시합니다. 문자열 하나를 가짜 연속 인용으로 재합성하지 않습니다.
2. 원문은 실제 STT를 불변으로 보존합니다. 인용 검증에서 같은 비어 있지 않은 화자의 인접 구간은 출처 범위를 추적해 대조할 수 있습니다. 서로 다른 화자가 끼어 있거나 출처가 비어 있는 구간을 하나로 잇지 않습니다. 원문을 임의 교정하거나 떨어진 문장을 이어 붙이는 방식은 거부합니다.
3. 각 요청은 기존 현재 요청/부정/예시/철회 검사를 거칩니다. 한 요청이 철회돼도 독립된 유효 요청까지 지우지 않습니다. 화자 교대 뒤 같은 화자의 취소가 앞선 요청을 무효화하는지도 별도 반례로 검증합니다. 화자 라벨만으로 경영주 신원을 확정하지 않습니다.
4. 단위 정정 요청은 '제대로 적어 달라'만 남겨 정정 대상이 사라지지 않게 앞선 같은 발화의 문맥을 보존합니다. 문맥에 있는 숫자/단위를 수령 필드에 새로 추출하거나 자동 복원하는 기능과는 구분합니다.
5. 모델 원응답은 보존합니다. 기존 저장 응답의 `requestQuote` 단일형은 명시적 호환 변환 후보로 검토하며, 새/구형을 동시에 주거나 잘못된 타입/초과 개수는 모호하게 합치지 않습니다. 질문·사실·센터 회신·부서·예산 계약은 바꾸지 않습니다.
6. UI에서는 기존 요청 편집 필드와 원문 대조를 사용합니다. 모든 분석에 일반 경고를 추가하거나 사람이 보지 않은 확인을 체크하지 않습니다. 회신 초안도 살아 있는 개별 요청을 다루되 센터의 최종 회신이나 처리 완료로 표시하지 않습니다.

## 검증 순서

- BMAD: 상담 과업의 세 요청 보존, 편집/원문 대조 UX, 모델 전용 호환 계약, 실제 근거·취소·미확인 검증을 나눕니다.
- First Bolt: 여러 발화 요청 하나가 비는 병목을 실제 음성으로 관측했습니다. 먼저 독립 합성 입력으로 실패를 재현하고 개별 인용 보존을 한 번 수정한 뒤 같은 입력으로 비교합니다. AI 검사는 사람 관찰로 세지 않습니다.
- 정상: 같은 화자의 인접 단위 정정, 서로 떨어진 세 요청, 단일 요청, 기존 저장 응답, 요청 없는 통화.
- 반례: 원문에 없는 문장/명령, 다른 화자가 끼어 있는 합성 인용, 과거/예시/계획/부정 요청, 복수 요청 중 하나 철회, 화자 교대 뒤 취소, 미확인 화자, 같은 문장 반복, 중복/순서 역전, 중복 제거 전9개 이상.

메인 구현 판단으로 다음 보수적 정책을 채택합니다. 사용자의 새로운 제품 범위 결정으로 표시하지 않습니다.

- R18/R19: 복수 후보에서 모호한 대명사 철회는 최근 요청으로 추정하지 않고 검토로 남깁니다.

- R23: 신·구 요청 key가 동시에 있으면 빈 배열이어도 모호한 혼용으로 처리합니다.

- R28: 정정 대상·값이 빠진 짧은 요청은 문맥을 임의로 보충하지 않고 검토로 남깁니다.
- R31: 일부가 철회된 복합 인용은 제외하되 별도로 제안된 원문 그대로의 생존 요청은 보존합니다.

유효 요청의 출처 span·원본 시각은 내부 resolver 결과에서 보존합니다. 정상 요청에 단순 출처 메타데이터용 경고를 추가하지 않으며 기존 issues는 실제 검토/거절 이유에 사용합니다. `fields.request: string|null` 및 공개 HTTP 계약은 유지합니다. 새 서버 구현과 독립 회귀 검증은 별도 단계입니다.
- 값 기대: 유효 요청의 원문·문맥 보존, 무효 요청 제외, null/검토 안내, 모델/전사 입력 불변. '전부 null'이나 '전부 통과' 구현은 양성/음성/변이 대조군에서 실패해야 합니다.
- 실제 모델 정확도와 무과금 계약 검사는 분리합니다. 이번 음성 canary의 실패 기록을 덮어쓰거나 후속 코드 재처리를 새 모델 성공으로 보고하지 않습니다. 추가 과금은 별도 메인 계획 전까지 없습니다.
