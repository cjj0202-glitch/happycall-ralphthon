# 접수 응답 유실과 중복 방지 설계

2026-09-21 pc1. 작은 검증 단위: 서버는 접수를 저장했지만 브라우저가 응답을 받지 못한 상황에서 같은 문의가 두 번 등록되지 않아야 합니다. 현재 POST는 요청마다 새 ID를 만들므로 이 상태의 사용자 재시도가 위험합니다.

## 계약

- 신규 웹 접수에 `X-Idempotency-Key` UUID v4를 보냅니다. 기존 키 없는 호출은 호환을 유지하지만 재시도 중복 방지를 보장하지 않습니다.
- 같은 키와 동일 JSON 본문은 최초 등록된 접수의 **현재 상태**를 반환합니다. JSON 키 순서는 무관하고 내용 변경은 409 `IDEMPOTENCY_CONFLICT`입니다. 새 접수나 이력을 추가하지 않습니다.
- 접수와 키 해시·본문 해시·접수 ID의 대응을 같은 JSON 문서 안에서 FileLock/atomic replace 또는 원격 CAS 한 번으로 저장합니다. 별도 메모리 캐시나 접수와 분리된 원장은 사용하지 않습니다.
- `GET /api/intake-attempts/{request_key}`는 해당 시도의 저장 결과를 조회합니다. 저장 기록이 없으면 404이며, 아직 처리 중인 요청이 없다는 뜻은 아닙니다. 같은 본문·키 재시도만 안전합니다.
- UUID 원문과 본문 해시는 일반 접수 목록/응답에 추가하지 않습니다. 이 키는 인증을 대체하지 않으며 기존 시연 접근제어가 그대로 필요합니다.
- 접수 본문의 유효성, 합성 근거의 명시 연결, 역할·revision 계약은 유지합니다. 과금 분석이나 PATCH를 자동 재시도하지 않습니다.

## 사용자 복구

브라우저는 접수 전에 시도 키와 본문을 묶습니다. 응답이 불확실하면 입력을 보존하고 저장 여부를 조회하며, 미확인 상태에서 다른 내용·새 키로 자동 재접수하지 않습니다. 조회 결과가 있으면 그 접수를 보여 줍니다. 없다면 같은 내용을 같은 키로 다시 전송할 수 있습니다. 명시적인 목록 갱신은 다른 역할 브라우저의 최신 접수를 읽는 별도 동작입니다.

## 검증

1. 양성: 같은 키/본문 2회, 새 repository 인스턴스로 재조회, 접수 1건·이력 1개.
2. 음성: 같은 키/다른 본문 409, 무효 키 422, 모르는 유효 키 404. 원본 상태 불변.
3. 경계: JSON 키 순서 변경, 서로 다른 키/같은 내용, 키 없는 기존 동작, 접수 수정 후 재시도는 최신 revision 반환.
4. 경합: local/CAS 두 호출 동시 시작에서 같은 키 1건, 다른 본문은 한 요청만 성공. 저장 뒤 timeout은 실패를 보존하고 조회로 실제 결과를 찾음.
5. 실제 HTTP/브라우저: 응답만 중단시킨 뒤 조회/재시도에서 중복 0건. 서버 실패를 성공으로 바꾸거나 조회 404를 미등록 확정으로 오인하지 않음.

실환경 Vercel 저장 검증은 관리자 저장소 연결 후 별도로 수행합니다. 메모리 CAS 테스트를 원격 영속성 완료로 계상하지 않습니다.
