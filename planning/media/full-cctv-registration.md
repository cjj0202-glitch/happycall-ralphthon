# 전체 CCTV 영상·좌표의 제품 등록

2026-09-22 pc1. 사용자에게 보여 줄 다음 결과는 WMS의 분기 공정에서 1080p 영상을 열고 같은 프레임의 합성 객체를 선택하는 화면입니다. 이 문서는 등록 전 설계이며 현재 생성 중인 영상의 완료 판정이 아닙니다.

## 입력과 사건 연결

- 단일 기존 렌더 PID13052, `.local/pc3-render-intake/full1080-a39cd66-01/animation`. 288 PNG와 최종 report·tracks·blend를 모두 생성하고 프로세스 종료가 확인된 뒤 검사합니다. 미완성 입력에는 완주 검사·패키징을 실행하지 않습니다.
- 별도 고정 기대값은 같은 부모의 `pc1-full-expectations.json`, SHA256 `1917e27f15157f14f95ad849386bdc93663b11bb62a5970810274efd9118c24b`입니다. 완성 보고서에서 기대값을 역산하지 않습니다.
- 실제 product fixture와 현재 tracks의 연결값을 읽어 CASE-0002 / W-W3 / SYN-CAM-02 / 2026-09-18T02:33:00+09:00 / CH-02 / D-02가 일치함을 확인했습니다. 최종 인수에서 다시 대조합니다. businessToteId는 null로 유지하며 SYN-VIS-PARCEL02를 업무 토트로 바꾸지 않습니다.
- `data/fixtures/cases.json`은 이미 같은 사건·카메라·이벤트·0~12초 구간을 등록합니다. 새 영상 hash·bytes는 `data/demo-media-manifest.json`에서 공급되므로 이 연결이 변하지 않으면 fixture를 수정하지 않습니다. 상담 원장 22건과 미저장 초안은 보존합니다.

## 검증과 공개 순서

1. M5 완주 검사로 291파일·입력 기대·최종 장면 readback·프레임 범위를 확인합니다. 여기의 PASS를 픽셀/전체 시각 품질 승인으로 쓰지 않습니다.
2. 수정 M6 도구를 독립 인수한 뒤 명시된 기존 FFmpeg7.1 실행파일로 새 후보 폴더에 인코딩합니다. H.264/yuv420p, 1920×1080, square pixels, 24fps, 288 디코드 프레임, 12초, 항등 표시행렬·faststart를 확인합니다. 원 tracks 바이트를 유지하고 descriptor의 videoSha256을 새 MP4에 연결합니다.
3. 메인이 `validate_candidate`로 정확한4파일·실제 바이트/해시·좌표와 영상 바인딩을 재검합니다. failure/staged/partial 파일이 남은 후보는 인수하지 않습니다. 마지막 검사 이후의 임의 외부 변경까지 방지한다는 보장은 하지 않습니다.
4. 실제 처음/분기 직전/분기/슈트/정착/끝 프레임을 열어 접촉·가림·화면 경계·식별성을 확인하고 전체 영상의 재생·탐색을 관찰합니다. 공개 전 미리보기는 기존 Next의 새 임시 자산 경로와 저장된 클로바 프로젝트의 기존 탭을 잠깐 사용하고, 완료 후 해당 탭을 원래 프로젝트로 돌립니다. 새 서버·브라우저를 시작하거나 상담 탭의 미저장 초안을 초기화하지 않습니다. 연속 픽셀을 전수 관찰하지 못했다면 플리커 전수 검증으로 표현하지 않습니다. 시각 판정을 숫자 검사로 대체하지 않으며 결함이 있으면 후보를 보존하고 품질 미달로 기록합니다.
5. 새 Release `demo-media-20260922-v4`의 물리 파일4개는 WAV2개+MP4+raw tracks입니다. 최상위 manifest 자산은 기존3개를 유지하고 tracks는 MP4 아래 정확한5필드 descriptor로 연결합니다. 보고서/원천업무자료/키/대화로그를 미디어 자산에 넣지 않습니다.
6. 새 공식 더빙이 먼저 준비되지 않으면 기존 v3 WAV2개를 바이트 그대로 유지하여 CCTV 업그레이드를 먼저 제공합니다. 국내 더빙·음질 인수는 미완료로 명시하고, 기존 음원의 길이·대화록·품질 기록을 새 음성 검증으로 바꾸지 않습니다. 최종 음성 목표를 축소하는 결정은 아닙니다.
7. Release digest와 독립 다운로드4/4를 확인한 뒤 manifest/로컬public 파일을 함께 등록합니다. 이전 자산·manifest는 로컬 버전 보관함에 보존합니다. 실제 자료를 배포 번들에 포함하지 않습니다.
8. 기존 Next 화면에서 WMS→W-W3→영상 열기→객체 선택→일시정지/프레임 전후→구간끝→닫기/포커스 복귀를 확인합니다. 타 사건·미등록 공정·불일치 좌표 실패도 확인하고390/768/1280폭을 검수합니다. 기존 서버를 재시작하거나 새 브라우저를 띄우지 않습니다.
9. 같은 최종 source/media로 새 생산 빌드·로컬 배포 묶음을 만들고 source/manifest/public/output/bundle 사본을 대조합니다. 영속 저장·실제 배포 URL·최신 API 전체 흐름은 별도 미완료 항목으로 남습니다.

## 등록 전 독립 검토 보완

읽기 전용 검토자가 순수 계약 함수로 최상위3→전달4파일과 v4 허용을 확인했습니다. 필수 tracked 변경은 `data/demo-media-manifest.json`이며 같은 사건·시각·구간을 유지하면 fixture 수정은 필요하지 않습니다.

기존 MP4의 승인된 교체를 위해 새 MP4 자산에 `sourceBytes: 1097133`, `sourceSha256: e6cad3cf9f999b596a0fef3e3d463170e0d279568a31a4be49366e5383908881`을 기록합니다. 현재 v3 자산의 정확한 값이며 교체 직전 실제 파일도 대조합니다. 이 값 없이 `--upgrade-approved`를 쓰면 `No approved source bytes/SHA256 for upgrade`로 거절되는 것을 검토자가 재현했습니다.

tracks는 신규 등록이며 기존 도구의 승인 업그레이드 대상3종에 포함되지 않습니다. 배포 위치에 다른 tracks가 이미 있으면 이름만 보고 덮지 않습니다. 모든4파일을 새 staging 폴더로 먼저 수신·검증하고, 기존 파일과 manifest를 로컬 버전 보관함에 바이트/해시 그대로 보존한 뒤 제품 자산을 함께 등록합니다. 실패 시 이전 버전으로 되돌릴 수 있어야 하며 미등록 기존 파일을 묵시적으로 신뢰하지 않습니다.

M6 소비자는 과거 생산자의 실패 이력을 복원하거나 발신자를 인증하지 않습니다. 실제 채택은 고정 `2c9f3e` 생산자 코드, 새 출력 폴더, 생산자 성공 반환, 소비자 재검증을 모두 요구합니다. 구본에서 남은 후보는 소비자만 PASS여도 채택하지 않습니다.

인수 근거는 `reports/pc3-full-render-main-start.md`, PC3 M5/M6 메인 인수 보고서, 실제 최종 영상 보고서에 연결합니다. PC3 도구 코드 통합·렌더 완주·영상 시각 승인·제품 등록·외부 배포를 각각 구분합니다.
