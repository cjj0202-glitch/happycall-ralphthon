# 통화·사이트 텍스트 인입 시연 설계안

**현재 적용:** DEC-013~015가 아래 제안보다 우선합니다. 접수정제와 근거확인 두 축을 포함하고, 경영주 입력/센터회신조회가 범위입니다. 현재 실험은 Astra Playwright 기술 검증이며 아래 사람2명/Silent Test 계획은 후속 미실시입니다.

상태: 실행 전 설계 초안. DEC-001~010의 결정과 미확정 AI 제안을 구분한다. 실제 녹음·모델 호출·화면·사람 관찰은 아직 없다. 시나리오별 수치와 문구는 실제 합성 fixture 계약을 고정한 뒤 채운다. 미도착·오출고 두 문의 유형에 통화·사이트 텍스트 두 접수 경로를 연결한다.

## 공통 흐름과 완료 상태

DEC-009·010 후속 결정: 아래 `handed_off`는 상담원의 이관 단계 완료를 뜻한다. 이후 센터 담당자가 사실·조치 결과를 확인하고 최종 회신을 담당한다. 확인·안내만 필요한 문의는 최종 회신 후 종결한다. 추가 확인·조치가 남으면 중간 회신 후에도 처리 중이며, 조치 완료와 최종 회신을 확인한 뒤 종결한다. 실제 회신 채널·시연 구현 방식은 아직 미결정이다.

경영주와 상담원의 모의 통화 종료 → 녹음 입력 → 대화록·정제 요약·접수서 초안 생성 → 상담원 입력과 발화의 차이/누락 확인 → 상담원 수정·조회 대상 확인 → 관련 WMS/TMS 근거 조회 → 사실/미확인과 답변 초안·부서 추천 → 사람 확인 후 저장·이관.

통화 후 검토에는 원문 발화와 AI 정제본을 함께 제공한다. 원문·음성 인식 결과·AI 요약·상담원 수정의 출처를 구분한다. 미확인 값을 임의로 보충하지 않는다. 접수 기본정보 검토와 최종 답변/이관 확인은 별도 확인 지점이다.

완료 상태 제안은 `handed_off`: 확인된 접수 내용, 연결 근거, 남은 확인사항, 담당 부서와 사람이 확인한 답변/확인 요청 초안, 수정·이관 이력이 저장된 상태다. 실제 배송 문제 해결·경영주 회신 완료와 구분한다. **DEC-008로 이관 허용 기준을 확정했다:** 점포·문의 대상·담당 부서가 식별되면 사실관계 미확인 항목을 확인 과제로 명시해 사람이 이관할 수 있다. 점포·문의 대상이 불명확하면 접수 확인 대기로, 부서 미식별이면 담당 확인이 필요한 상태로 남긴다. 필수 식별키는 문의 유형별로 정한다.

## 시연 A — 미도착 문의

- 입력 대본 제안: 아직 배송을 받지 못했다는 경영주 진술에 불만·반복 표현·모호한 도착 시각을 포함한다. 점포·배송일 등 실제 조회키는 합성 fixture에 맞춘다.
- 정제 기대: 불만의 의미와 도착 여부 확인 요청을 보존하고 욕설·반복 표현은 업무 문장으로 정리한다. 경영주의 진술을 시스템 실적으로 바꾸지 않는다.
- 근거: TMS 계획·점포 방문 순서·실제 도착 기록 상태, 연결된 WMS 출고 정보를 표시한다. 도착 기록이 없으면 미도착/기사 귀책을 확정하지 않는다.
- 결과: 미확인 항목과 근거를 포함해 배송 확인 담당 부서에 확인 요청을 준비한다. 실제 부서명은 합성 담당 기준으로 매핑한다.

## 시연 B — 오출고 문의

- 입력 대본 제안: 주문 상품과 받은 상품이 다르다는 진술, 수량·단위의 모호함 또는 상담원이 잘못 옮긴 입력 한 항목을 포함한다. 실제 상품·수량은 합성 fixture에 맞춘다.
- 정제 기대: 주문 기대 상품과 받은 것으로 진술한 상품을 분리한다. 예를 들어 박스/개 단위가 다르면 환산 근거 없이 값을 확정하지 않는다.
- 근거: 주문·피킹 스캔·소터 이동·출고를 상품행·토트·시각으로 연결한다. 소터 이벤트는 기존 킷에 없으므로 합성 확장 계약이 준비되기 전에는 미확인으로 둔다. 실제 데이터에 맞춰 상품·수량 또는 토트 연결의 차이를 표시한다.
- 결과: 출고 담당 부서에 근거와 차이를 전달한다. 출고 기록상 차이와 경영주가 받은 실물의 확인 여부를 구분한다.

## 시연 C — 해피콜 사이트 텍스트 접수 추가

- 입력 예시 제안: 오출고 문의의 제목·본문·점포/상품 등 제공된 입력 필드. 실제 경영주의 글을 복제하지 않고 합성 예시를 작성한다. 두 통화 시연 A/B는 유지한다.
- 접수 후 처리: 사이트 접수 원문 보존 → 욕설·반복 표현 정제 → 상품·수량·단위·요구 추출 → 누락/모순 표시 → 담당자 확인 → WMS/TMS 근거 → 답변 초안·부서 확인/이관.
- 음성과의 차이: STT가 필요 없고 근거는 발화 시각 대신 원문 문장·입력 필드다. 원문과 구조화 입력이 다르면 한쪽을 자동 정답 처리하지 않는다.
- 성공 기준 제안: 사이트 제목·본문의 핵심 요구를 보존하고, 관련 근거와 담당 부서까지 연결한다. 미확인 필드는 그대로 유지한다.
- 제약: 생성된 동일 물류 fixture를 재사용해도 통화 접수에 연결된 기존 call_id를 새 텍스트 접수의 출처로 붙이지 않는다. 별도 인입 식별자와 사례 연결을 계약으로 정한다.
- 조합 검증 제안: 통화/텍스트 × 미도착/오출고 4조합의 입력 계약을 확인한다. 기존 시연 반복 횟수·평가 분모를 자동 변경하지 않으며 검증 계획 확정 시 정한다.

## 상태와 실패 처리 제안

| 상태 | 표시·행동 | 확인할 기준 |
|---|---|---|
| 입력 전 | 종료된 모의 통화 선택 | 케이스·파일 식별, 합성 여부 표시 |
| 처리 중 | 음성 인식/정제 진행 표시 | 완료 전 결과를 확정본으로 표시하지 않음 |
| 처리 실패 | 실패 단계·보존된 입력·재시도 | 실패를 빈 접수서 성공으로 처리하지 않음 |
| 검토 필요 | 원문·정제·입력 차이·미확인 | 상담원이 원문 근거로 수정 가능 |
| 조회/이관 준비 | 근거·초안·추천 부서·남은 확인사항 | 다른 케이스 기록 혼입 및 없는 사실 확정 방지 |
| 이관 저장 | 확정본·담당 부서·이력 | 중복 저장 방지, 미확인 항목 보존 |

## 첫 Bolt 추천 — 정제된 접수서의 정확성

새 사용자 설명의 핵심은 욕설·불명확한 발언과 상담원 오류가 잘못된 접수·이관으로 이어지는 것을 줄이는 것이다. 첫 실험은 이 입력 품질을 한 케이스로 시험하는 안을 추천한다. 기존 도착 누락 판정은 이후 같은 케이스의 물류 근거 검토에 연결한다. 첫 실험 축소가 통화 처리·WMS·TMS 전체 요구의 제외를 뜻하지 않는다.

- 과업 제안: 종료된 모의 통화와 접수 초안을 보고 접수 내용을 검토·정리해 다음 단계로 넘길 준비를 한다. 시험 중 오류 위치나 정답은 알려주지 않는다.
- 참가자 제안: 2명 이상, 실제 상담 경험과 같은 화면의 사전 노출 여부 기록. 팀원만 참여하면 팀 내부 사용성 관찰로 명시한다.
- 성공 기준 제안: 도움 없이 심어 둔 입력 오류를 찾고 원문 근거로 수정, 핵심 요구사항 보존, 누락 정보를 추정하지 않음. 목표는 참가자 2/2가 2분 안에 과업 완료하되 아직 미합의·미측정이다.
- 관찰: 첫 행동·근거 발화 발견·수정 위치·시간·도움·잘못된 확정·이관 준비 여부. 의미를 왜곡하거나 누락 정보를 사실로 만든 경우 실패로 기록한다.
- 이후: 가장 큰 문제 하나만 수정하고 같은 과업으로 재시험한다. 참가자 학습 효과를 남긴다.

## 개발 전 남은 조건

1. 첫 Bolt 선택·시간/성공 기준, 녹음 입력 방식·실제 AI 범위 구체화.
2. 두 케이스의 실제 합성 키·정답·소터 이벤트·부서 매핑 계약 확정.
3. pc2~4 준비 보고의 hostname·계정·역할 연결, 실제 등록 PC의 편지함 왕복 검증.
4. Astra Ultra 실제 적용 확인, 실제 Goal·로그 보존 시작 조건 충족.

병행 작성된 docs/18은 데모 전용 API와 개발 replay 원칙을 기록한다. 해당 변경을 보존하며 이 설계 작업에서는 실제 API를 호출하지 않는다. API 키 파일·비밀값은 이 문서에 포함하지 않는다.
