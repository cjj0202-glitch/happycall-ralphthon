# 저장과 함께 남기는 알림 의도 — 1단계 상세 설계

2026-09-22 pc1. 최종 카카오톡·Teams 연동을 위해 이관·센터 회신의 알림 의도를 접수 저장과 함께 보존합니다. 현재 공급자 연결·수신자 매핑이 없으므로 실제 발송은 하지 않으며 `연결 안 됨`으로 표시합니다. 외부 수신까지 구현해야 한다는 최종 범위는 유지합니다.

## 과업과 소유

기준은 main `853e215d8ef7fba7062109f7e2d66aa4c9a216d1`, 정본은 `role-workflow-and-notifications.md`입니다. PC4 N04-D2가 소유한 공급자 계약·검토 문서는 유지하며, 메인이 서버 저장 경계와 공통 UI 계약을 맡습니다. 별도 발송 프로세스·외부 API·계정/권한 변경·유료 호출은 이 단위에 포함되지 않습니다.

BMAD 관점에서 사용자는 저장 성공과 알림 전달 성공을 구분해야 합니다. UX는 기존 처리 버튼을 늘리지 않고 저장된 사건의 알림 상태만 보여 줍니다. 구조는 접수와 같은 원자적 문서에 알림 의도를 저장하고, 검증은 저장 실패 시 알림도 없음과 중복·다른 사건 혼입 방지입니다. 작은 Bolt 가설은 “이관 저장 성공이 Teams 전송 성공으로 오해되지 않는다”이며, 먼저 저장/충돌 반례와 명시적인 연결 안 됨 상태를 확인합니다. 사람 관찰은 별도입니다.

## 업무 사건과 대상

| 확정된 변경 | 알림 종류 | 논리 대상 | 채널 | 이번 상태 |
|---|---|---|---|---|
| 상담 검토 → handed_off | handoff | 저장된 담당 부서 | teams | not_connected |
| 센터 회신 본문 변경, 종결 전 | interim_reply | 이 사건 담당 상담원 | teams | not_connected |
| 센터의 closed 전이 | final_reply | 이 사건 담당 상담원 | teams | not_connected |
| 센터의 closed 전이 | final_reply | 저장된 점포 경영주 | kakao | not_connected |

같은 요청에서 회신과 종결이 함께 저장되면 final_reply만 생성합니다. 이미 등록한 센터 회신을 그대로 두고 조치를 마친 뒤 종결해도 final_reply를 생성합니다. 같은 본문 재저장, 조치 목록만 변경, 담당 부서 초안 편집, AI 분석, 단순 조회에서는 새 알림을 만들지 않습니다. 중간 회신의 경영주 외부 알림 정책은 아직 확정하지 않아 생성하지 않습니다. 현재 없는 ‘추가 확인 요청 등록’ 모델은 이미 구현됐다고 가정하지 않습니다.

논리 대상은 실제 Teams 사용자나 카카오 수신 전화번호가 아닙니다. recipientRef에는 역할과 원본 식별값의 SHA256만 남기고 점포 입력값 자체를 복사하지 않습니다. 자유 입력에 전화번호·URL이 들어 있어도 알림 의도에 전파하지 않습니다. 수신자 식별/권한 대조와 공급자 설정을 마치기 전에는 발송 가능 상태로 승격하지 않습니다. 저장된 점포 식별이 비어 있으면 recipientRef는 null, reason은 missing_recipient로 연결 미완료 상태를 유지합니다.

원본 식별 우선순위는 center=검증된 departmentId, owner=저장된 intake.storeId(상위 store.id로 대체하지 않음), counselor=caseId입니다. 상담원 식별은 현재 모델에 없으므로 counselor ref는 사건 단위 미배정 논리 대상입니다. 이후 실제 담당자/수신처 검증을 대신하지 않습니다.

## 저장 계약

1. `CaseService.patch`의 기존 역할·revision·필수 필드·전이·종결 검증을 모두 마친 뒤 같은 transform에서 `notificationOutbox`를 추가합니다. 네트워크 부작용은 transform 내부에 없습니다.
2. optional 배열의 각 레코드는 schemaVersion(정수1), id(64자리 소문자 SHA256), caseId, caseRevision, kind, channel, recipientRole, recipientRef, createdAt, status, reason의 11필드만 허용합니다. 원문·욕설·회신 본문·연락처·키·임의 URL은 복사하지 않습니다. 메시지/인증된 상세 링크는 실제 전달 계약에서 별도 구성합니다.
3. caseRevision은 현재 revision+1이며 repository의 실제 저장 revision과 같아야 합니다. ID는 스키마 버전/사건ID/저장revision/종류/채널/논리대상의 결정적 SHA256으로 만듭니다. 시각은 ID 재료가 아닙니다.
4. 기존 배열과 새 의도를 합칠 때 같은 ID를 중복 추가하지 않습니다. 같은 revision의 PATCH 재전송은 기존 STATE_CONFLICT로 거절되며 outbox도 변하지 않습니다. 최신 revision에서 같은 의미의 상태/본문을 재저장해도 새 의도는 없습니다.
5. 교체 전 JSON 저장 실패·확정 CAS 미저장·다른 작업자의 같은 사건 변경에서는 접수 변경과 새 의도가 함께 반영되지 않아야 합니다. 다른 사건 CAS 충돌 후 재시도에서는 transform을 다시 호출하지 않으며 최종 한 세트만 저장합니다. timeout이나 성공 후 응답 유실은 미저장으로 단정하지 않고 저장된 사건을 다시 조회해 확인합니다. 새 알림을 별도로 쓰거나 네트워크 재시도로 보정하지 않습니다.
6. 기존 알림 필드가 없는 22건은 읽기·마이그레이션으로 임의 알림을 생성하지 않습니다. 새로운 정상 전이에만 배열이 생깁니다. 과거 이관·회신을 자동 소급 발송하지 않습니다.
7. 클라이언트 PATCH에서 notificationOutbox를 직접 보내면 기존 immutable-source 가드로 거절합니다. 이 배열은 서버가 저장한 의도이며 클라이언트 발송 확인이나 사용자 인증 증거가 아닙니다.
8. 실제 전달 worker는 향후 별도 내부 저장 계약이 필요합니다. 업무 PATCH로 종결 잠금을 풀거나 업무 revision/history를 발송 상태 갱신에 쓰지 않습니다. 이번 단계에 실제 발송 worker나 전송 성공 상태는 없습니다.
9. 저장된 배열은 업무 변경 전에 현재 revision 이하인지 검증합니다. 아직 저장되지 않은 다음 revision의 행을 기존 기록으로 허용하지 않습니다. 같은 transform 안에서만 다음 revision의 결정적 ID를 허용해 중복 추가를 막습니다. counselor 참조는 그 사건 ID의 해시와 일치해야 합니다. 과거 owner/center 참조는 현재 담당·점포 변경으로 덮어쓰지 않습니다.

## 실행 검증

합성 임시 JSON 저장소와 메모리 CAS에서 실행합니다. 실제 `.local/cases-store.json`, 원장, 실행 중 API는 열거나 변경하지 않습니다.

- 정상: 이관1개, 중간회신1개, 최종회신2개, 회신 변경 없는 종결2개; 저장 revision과 일치.
- 음성 반례: 저장 실패·미확인 이관·권한 위반·조치 미완료 종결·낡은 revision·직접 outbox 주입은 새 의도0이며 문서/버전 불변.
- 경계: 같은 본문 재저장0, 조치 변경0, 빈 대상은 missing_recipient, 기존 필드 없는 문서 읽기0, 두 사례 ID/대상 분리.
- 동시성/복구: 다른 사건 CAS 충돌 후 한 세트, 같은 사건 충돌 새 의도0, 저장 후 응답 유실 뒤 재조회에 한 세트 보존.
- 개인정보: 원문·회신·전화번호·URL 모양 sentinel이 의도에 포함되지 않음. 채널과 역할 매핑의 허용 조합만 생성.
- 변이: 이벤트 중복 억제 제거, 동일 저장 대신 저장 후 추가 같은 결함을 실제 검사에서 검출.

새 API 경로나 새로운 서버를 시작하지 않습니다. 코드 인수·ASGI 통과와 실행 API 반영·실제 수신은 각각 별도로 기록합니다. 이 단계 이후에는 PC4 계약 인수 → 수신자/채널 구성 → 영속 발송 상태·불명확한 응답 대조 → 실제 채널 수신 검증이 남습니다.

## 표시 UI 브리프

기존 업무 워크벤치와 `apps/web/app/tokens.css`를 유지합니다. 새 메뉴·색·폰트·설정 버튼을 추가하지 않습니다. 접수 저장/센터 회신 영역 아래 작은 접이식 ‘외부 알림’ 패널을 두고, 닫혀 있어도 ‘연결 안 됨’을 표시합니다. 내용을 열면 저장된 알림 종류·채널·논리 수신 역할·시각과 실제 전송되지 않았다는 안내를 보여 줍니다. 내부 해시/recipientRef는 화면에 표시하지 않습니다.

경영주 화면에는 경영주 대상 카카오톡 기록만 보이고 상담원·센터 화면에는 해당 접수의 업무 기록을 표시합니다. caseId가 다른 기록·알 수 없는 종류/채널/역할/상태/필드 형식은 원시 값을 노출하거나 성공으로 바꾸지 않고 ‘기록 확인 필요’로 보류합니다. 기존 필드 미존재는 ‘저장된 알림 기록 없음’이며 과거 외부 발송0건을 단정하지 않습니다. 서버에 저장된 Case를 읽고 편집 중 초안으로 이벤트를 만들지 않습니다.

정상/비정상/빈 기록·다른 사건 혼입·원문 sentinel·역할 필터의 실제 React 렌더 검사와 기존 열린 화면의 빈 상태·접기/펼치기·3폭을 검수합니다. 새 서버에 알림 기록이 저장되는 전체 브라우저 흐름은 현재 API 재시작 거부가 해소될 때의 별도 항목입니다.

## 구현 전 독립 대조

읽기 전용 검토자가 실제 repository 함수에 메모리 transform을 주입해 다른 사건 CAS 충돌(transform1/CAS2/outbox1/revision일치), 같은 사건 충돌(STATE_CONFLICT/outbox0), 교체 전 JSON 실패(문서불변), legacy읽기(의도0/쓰기0), 직접주입(IMMUTABLE_SOURCE)을 확인했습니다. 수신자 원시 입력에 전화번호·URL이 들어갈 수 있다는 지적을 반영해 해시화와 위 원천 우선순위를 고정했습니다. 동일 회신의 revision/history 증가가 이벤트 생성을 뜻하지 않는다는 점도 수용 기준에 남깁니다. 이는 저장 구조의 설계 인수이며 새 구현의 통과 판정은 아닙니다.
