# 4PC 랄프톤 실행계획

**현재 우선 기준은 DEC-013~015, [통합 프롬프트](../PROMPT_team.md), [미실행 /goal 초안](../GOAL.md), [공유 컨텍스트](21_공유_작업컨텍스트.md)입니다.** 초기 45개 작업표의 완료선을 유지하면서 아래 로컬 착수 예외를 적용합니다. 문서 보완은 실제 Goal 실행·로그 제출·사람 관찰 완료가 아닙니다.

## 1. 정본과 역할

설계·실행 코드·작업 상태는 이 저장소가 정본입니다. 킷은 별도 저장소의 재사용 도구이며 `ops/baseline.json`에 읽은 SHA를 고정합니다. 채팅·이슈 합의는 관련 설계에 옮긴 뒤 사용합니다. 원본 킷 전체를 복사해 두 개의 정본을 만들지 않습니다.

| 슬롯 | 초기 제안 역할(현재 배정 아님) | 초기 소유 후보 | 첫 사전 준비 | 초기 제품 후보 |
|---|---|---|---|---|
| pc1 | 통합·계약·검증·발표 | contracts, ops, 공통 셸, 배포 설정 | 행사 조건·계정/슬롯 등록 | 공통 타입·fixture·기본 셸 |
| pc2 | 합성 음성·영상·자산 | assets, media 도구 | 미디어 패키지·재생 점검 | 두 케이스의 작은 합성 자산 묶음 |
| pc3 | 근거 조회·작업대 | evidence UI·repository | 브라우저·빌드 점검 | 누락/충돌을 보존하는 조회 공급자 |
| pc4 | 접수·답변·평가 | intake·decision 서비스 | Python·모델 권한 여부 확인 | 발화 출처가 있는 접수 fixture 공급자 |

위 역할표는 초기 배치 제안이며 현재 신원·담당은 `channel/pcs.json`과 메인이 보낸 작업 카드가 정본입니다. 실제 사람·hostname·GitHub를 대조해 등록하고 TEST 왕복 후 원격 제품 작업을 배정합니다. 신원 미등록 상태에서도 읽기 전용 점검은 가능합니다. 같은 노트북의 대기 세션1~6은 다른 원격 PC가 아닙니다. 현재 `apps/web`·`server`를 초기 `contracts`/`assets` 후보 경로로 임의 이동하지 않습니다.

## 2. 설계·실험·배정의 순서

**DEC-013 실행 예외:** 사용자가 시간 제약에 따라 로컬 병렬 구현과 Astra Playwright 검증을 먼저 요청했습니다. 따라서 아래 초기 G02·L01·UX03 선행표는 기존 작업 인수 기준으로 보존하되 로컬 승인 작업을 다시 중단시키는 조건으로 사용하지 않습니다. 원격 PC 등록·TEST 및 경로 소유 확인은 실제 원격 배정 전에 수행합니다. Playwright 결과를 실제 사람 Silent Test로 대체 표기하지 않고 사람 관찰은 미완료로 남깁니다. 실제 /goal은 아직 실행 전 초안이므로 기존 구현 로그를 Goal 실행으로 소급하지 않습니다.

다음은 **초기 정규 게이트 계획**입니다. 현재 착수 예외 및 배정 카드를 함께 적용합니다.

- **독립 준비:** S01 운영 패키지 이후 G01 공식·예산 조건, R01 등록→R02~R04 노트북 점검, P01 킷 재현을 준비합니다. 공식 로그인 U00과 교육 원본 대조 SRC01도 별도로 추적합니다. 자료 읽기와 로컬 준비는 회의와 병행할 수 있습니다.
- **4인 설계:** B01 문제·성공 기준·결정 책임 → B02 여정·기능 포함/제외·First Bolt 선택 → P02 실제 데이터 계약·fixture → B03 공유 구조·검증·소유 경계 → P03 설계 대조입니다. B02는 P01의 실제 데이터도 확인해야 합니다. [회의 방법](13_4인_설계회의와_BMAD.md)에 따라 네 사람의 의견과 결정 이유를 남깁니다. B01~B03 논의에 모든 PC의 설치 완료를 요구하지 않습니다.
- **제품 배정 게이트:** G02는 P03과 R02~R04가 모두 DONE인 뒤 4PC 역할·편집 경로·첫 작업을 확인합니다. 이후 L01 실제 개발 Goal 시작·로그 보존 → S02 앱 골격을 진행합니다. 역할 제안이나 배정 후보 표는 실행 지시가 아닙니다.
- **작은 실험:** S02 → UX01 First Bolt 최소 화면·실제 관찰 → UX02 중요한 변경 하나·같은 과업 재시험 → UX03 실제 재검증·handoff를 진행합니다. [FDE 적용안](16_FDE_First_Bolt_적용.md)의 참가자·과업·기준을 실행 전에 고정합니다. P0 근거/접수 확장 E01·I01은 UX03이 DONE인 뒤 배정합니다. M01/M02 미디어 준비는 G02 이후 이 실험과 병행할 수 있습니다.
- **확장·제출:** 의존성이 충족된 덩어리 하나 → 워커 검증 → pc1 통합 검증 → DONE입니다. 실제 사용자 관찰, 제품 정확성 평가, 통합 시연은 서로 다른 검증이며 하나로 다른 것을 대체하지 않습니다.

BMAD는 설계 산출물과 역할 관점, Grill-me는 질문과 가정 검토, Bolt는 작은 학습 실험, Ralph는 정해진 덩어리의 구현·검증에 적용합니다. 자세한 기능 후보와 장기 비전은 [기능 검토표](../planning/features.md)와 [솔루션 지도](../planning/solution-map.md)에서 결정합니다. 큰 솔루션의 범위를 논의하더라도 이번 행사에서 입증할 결과와 이후 제품 범위를 구분합니다.

| 설계·실험 작업 | 반드시 남길 결과 | 완료로 보지 않는 것 |
|---|---|---|
| B01 | `reports/design/B01-product-brief.md`: 주사용자·PoV/HMW·성공 측정·실제 네 사람 의견·결정자 | AI가 가상의 4인 의견을 작성한 상태 |
| B02 | `planning/features.md`, `planning/solution-map.md`: 여정/Flow·채택/제외 이유·실험 가설/판정 기준 | 후보 목록이나 예시 화면만 만든 상태 |
| P02·B03 | 실제 계약/정답 fixture와 `reports/design/B03-decisions.md`: 경계·책임·반례·통합 계획 | 데이터 확인 없이 구조에 동의한 상태 |
| UX01~03 | `experiments/bolt/1_bolt.*`부터 3 버전, 각 `*_test_result.md`, `handoff.md` | 계획·AI 화면 분석·버전 증가만 있는 상태 |
| SRC01 | `reports/FDE-source-review.md`: 원본 11개·10분할 전수 열람·웹 접근 결과·차이 반영 | 브리핑만 읽고 11장 검증을 완료했다고 표시 |

SRC01은 자료 보완 작업이며 현재 B01~UX03의 필수 선행 작업이 아닙니다. 원본 미수신/웹 접근 제한은 출처별로 표시하고 검증된 브리핑·공식 방법론을 바탕으로 논의는 계속합니다. 원본 도착 후 중요한 차이가 발견되면 해당 결정과 영향을 받는 작업만 다시 검토합니다. Vercel H01/H02는 사용자 재개 요청 전까지 시작하지 않습니다.

## 3. 작업표 사용법

`ops/tasks.json`이 기계 정본, `TODO.md`가 사람이 읽는 생성 화면입니다. 표를 직접 체크하지 않습니다. `next`는 후보를 보여줄 뿐 배정·발송하지 않습니다.

```powershell
python ops/tasks.py status
python ops/tasks.py next --pc pc3
python ops/tasks.py show E01
python ops/tasks.py check
```

중앙표를 고치는 사람은 pc1 한 명입니다. 한 PC의 `DOING + REVIEW`는 최대 1개이며, 의존 작업이 DONE이 아니거나 담당 PC가 미등록이면 시작 명령이 거부됩니다.

```powershell
# pc1: 배정할 때
python ops/tasks.py start E01
# 워커: 증거 템플릿을 파일에 저장하고 실제 관측 결과를 채운다
python ops/tasks.py template E01 > reports/E01.evidence.json
# pc1: 회신의 커밋과 파일을 확보한 뒤
python ops/tasks.py review E01
python ops/tasks.py accept E01 --evidence reports/E01.evidence.json
python ops/tasks.py check
```

Windows PowerShell 5.1의 `>`는 UTF-16일 수 있습니다. 그 환경에서는 `python ops/tasks.py template E01 | Set-Content -Encoding UTF8 reports/E01.evidence.json`을 사용합니다. 증거 읽기는 BOM을 허용합니다.

증거 파일에는 작업 ID·완료 기준 해시·측정 시각·관측자·항목별 기대/실측·필수 산출물 경로가 필요합니다. 도구는 누락·실패·경로 이탈·완료 기준 변경을 거부합니다. **관측 내용의 진실을 자동 판정하지는 않으므로 메인이 원본 결과를 열어 재현해야 합니다.** 완료 산출물의 해시는 남기고, 이후 변경되면 `check`가 재검토를 요구합니다.

거절: `reject ID --reason ...`로 TODO. 막힘: `block ID --reason ...`; 해소: `resume ID --reason ...`. DONE의 범위가 늘어나면 후속 작업으로 추적합니다. 기존 완료 산출물의 수정은 pc1이 다시 검증한 뒤 `reverify ID --evidence 새증거파일 --reason 재검증사유`로 갱신합니다. 이전 해시는 history에 보존됩니다. 텍스트 해시는 Windows 줄바꿈을 LF로 정규화하고 바이너리는 원본 바이트를 사용합니다. `render`는 중단 후 작업표 재생성에도 사용합니다. `.tasks.lock`이 남으면 해당 PID가 살아 있는지 확인하고 죽은 프로세스의 잠금만 지웁니다.

## 4. 한 번의 워커 루프

1. `AGENTS.md` → `PROMPT_team.md` → 공유 컨텍스트·`CURRENT_TODO.md`·`TODO.md` → 맡은 작업 ID와 현재 계약을 읽습니다. 실제 실행할 /goal은 별도 원문·모델/강도·시각·HEAD를 보존합니다.
2. `whoami`와 실제 branch/commit을 확인합니다. 기존에 배정된 열린 편지는 시작할 때 한 번 확인합니다. 이후 `watch --once`는 **변경 알림**일 뿐 미처리 업무 목록이 아닙니다.
3. task branch에서 한 덩어리를 구현합니다. 공통 계약이 필요하면 먼저 샘플로 맞추고 경로 소유자에게 메인을 통해 요청합니다.
4. 명시된 기대값과 비교합니다. 실패하면 최대 두 번 방법을 바꾸어 보되 동일 오류 3회 또는 30분 막힘이면 멈춰 결정 요청합니다.
5. 산출물·검증 기록을 커밋하고 해당 branch를 push합니다. 이슈에 task ID·SHA·증거 경로·실측·남은 문제를 한 번 회신합니다.
6. 메인은 그 SHA를 실제로 읽고 통합·검증합니다. `accept` 이후에 이슈를 닫고 다음 작업을 배정합니다. 워커는 스스로 완료 체크하거나 중앙표를 merge하지 않습니다.

일감이 없으면 종료합니다. 무한 자기호출·권한 생략 플래그·자동 배포는 이 절차에 포함되지 않습니다. 감시기는 읽기 전용이며, 멈춘 Astra/Claude 세션을 깨우는 자동화는 별도 설정입니다. 이번 패키지는 그러한 자동화를 켜지 않습니다.

## 5. 브랜치·통합 규칙

`work/pc3-E01`처럼 슬롯·작업 ID로 branch를 만듭니다. 동시에 같은 파일을 수정할 필요가 생기면 pc1이 소유 경계를 먼저 조정합니다. 각 워커는 자기 변경 경로만 커밋합니다. 작업 중 다른 사람의 변경을 stash/reset하지 않습니다.

pc1은 테스트가 붙은 커밋을 순서대로 통합하고, 잠금 파일·공통 타입·의존성 버전은 pc1이 관리합니다. push 뒤 원격 SHA를 확인합니다. 다른 PC의 적용 완료는 해당 PC의 HEAD·테스트 회신으로만 판단합니다.

같은 PC에서 서브에이전트를 병렬로 쓰는 경우에도 조사·검토·서로 다른 소유 경로처럼 독립 가능한 범위만 나눕니다. 중앙 `ops/tasks.json` 쓰기와 통합·인수는 pc1이 직렬 처리합니다. 서브에이전트의 완료는 실제 네 사람의 회의 참석이나 다른 노트북의 준비 완료를 뜻하지 않습니다. UX01→02→03처럼 앞 관찰 결과가 다음 입력인 실험을 동시에 진행하지 않습니다.

## 7. 방법론·공식 배점과 배정 증거

BMAD는 업무/UX/구조/QA의 검토 관점, Grill-me는 아직 필요한 핵심 결정 질문, First Bolt는 작은 가설→관찰→한 가지 수정→재시험, Ralph는 승인된 결과의 구현·검증 반복입니다. 자세한 실행 프로토콜은 `PROMPT_team.md`를 따릅니다. 첫 Bolt의 접수 단위 오류와 근거의 사실/미확인 실험은 분리하고 두 결과 모두 제품에 반영합니다.

공식 활용20·Goal20·결과 위임30·완료검증30을 작업 카드의 결과·명령·기대/실측·실패수정·동일조건 재검증과 연결합니다. 이 수치는 확보 점수가 아닙니다. 메인이 증거를 읽어 인수한 뒤에만 TODO 체크·이슈 종결합니다. 20입력·12경계·6회 완주·3명 업무시간 비교는 별도 평가이며 다른 검사 개수로 통과 처리하지 않습니다.
