# 점수 전략 — 결과·위임·검증을 연결한다

공식 배점 정본은 [09](09_공식규정_전수대조.md). 아래는 **우리 팀의 준비 전략**이며 공식 채점 세부 산식이나 점수 보장은 아닙니다. 제품 성공 기준을 충족하면서 그 과정을 검증 가능한 제출물로 만드는 것이 목표입니다.

계획과 실행을 분리한 현재 대조는 [점수 대응 실측](../reports/scoring-review.md)입니다. 고정 20건 정확도 70.83%와 안전 실패 5건을 보존하고 수정 중이며, 자동 필드 검사만으로 90% 목표 달성을 주장하지 않습니다. 야간 [운영 스킬](../.agents/skills/happycall-night-ops/SKILL.md)은 같은 실패의 수정·재시험·커밋·인수 근거를 연결합니다.

## 1. 무엇에 시간을 쓸 것인가

1. **결과 중심 위임 + 완료·검증 = 60점 영역을 먼저 완성**합니다. 상담 담당자가 어떤 판단을 끝낼 수 있는지 Goal에 쓰고, 구현 선택은 에이전트에 맡기며, 실제 동작·실패 수정으로 검증합니다.
2. **Goal 기본 구성 20점**은 원문 자체에서 목표·완료 상태·확인 기준·제약이 빠지지 않도록 합니다. 설계에만 써놓고 실제 지시에 빠뜨리지 않습니다.
3. **활용 기록 20점**은 실제 로그를 잃지 않고 설명할 수 있게 합니다. 실행 시간·턴·토큰·API 규모를 구분하고, 허위 실적이나 중복 파일로 부풀리지 않습니다.
4. 결선은 실제 업무 사용 의향을 설득해야 합니다. 누락을 숨기지 않는 미도착 사례, 출고 차이를 찾는 오출 사례, 사람 확인을 두는 이유를 짧은 시연으로 보여줍니다.

고득점 준비의 종료 기준은 각 공식 항목에 실제 증거가 연결되고, 다른 사람이 같은 결과를 재현할 수 있는 상태입니다. 공개되지 않은 구간별 점수를 임의로 합산해 '예상 100점'으로 발표하지 않습니다.

## 2. 항목별 증거 묶음

| 공식 항목 | 우리가 보여줄 주장 | 1차 증거 | 교차 확인 | 막을 실수 |
|---|---|---|---|---|
| 활용 기록 20 | Astra가 계획뿐 아니라 구현·실행·수정을 수행 | 실제 주요 JSONL, 로그 manifest | 커밋 시각·실행 결과·중단/개입 기록 | 긴 시간=높은 점수라고 단정, 턴을 에이전트 수로 표시 |
| Goal 20 | 사용 결과·제약·완료선이 처음부터 전달됨 | 실제 goal-used 원문 | 입력이 있는 주요 로그 | 사후 작성 초안을 실제 사용 원문으로 제출 |
| 결과 중심 30 | 상담자의 근거 확인·답변/이관 완결을 위임 | 두 시나리오 Goal·자율 판단 범위 | 실제 구현 선택·계약 결정·UI 흐름 | 파일/기술 지시만 있고 사용자 결과가 없음 |
| 완료·검증 30 | 정상뿐 아니라 누락·충돌·실패를 확인하고 고침 | evaluation·rehearsal·수정 전후 | 원본 fixture·테스트·화면·재실행 | 테스트 계획만 제출, 실패/건너뜀을 통과 처리 |

가장 강한 근거 세트는 **Goal의 완료 기준 → 실행 결과 → 결함 → 수정 commit → 같은 검증 재실행 → 남은 한계**입니다. 이 사슬이 이어지는 사례를 하나 이상 확보합니다. 실패를 일부러 만들거나 이미 성공한 작업을 불필요하게 반복해 기록을 늘리지 않습니다.

## 3. Goal과 4PC 작업 분할의 균형

대표 Goal은 'OneFlow를 두 시나리오로 검증 가능한 상태까지 완성'이라는 결과를 맡깁니다. 내부 TODO의 30~90분 덩어리는 의존성·충돌을 줄이는 운영 수단입니다. 한 줄 구현을 할 때마다 사람이 허락해야 하는 절차로 만들지 않습니다.

pc1은 승인된 설계·범위 안에서 준비된 작업을 고르고 분담·검증합니다. pc2~4는 구현 방식, 세부 코드 구조, 검증 가능한 오류 수정에 재량이 있습니다. 사용자 결과·계약·예산·데이터 공개 범위가 바뀌는 경우에만 중요한 결정으로 올립니다. 추가 지시가 필요했다면 원인과 효과를 남기고 감추지 않습니다.

4개 계정의 로그는 네 개의 실제 실행 출처입니다. 병렬성 자체를 점수로 환산하지 않습니다. pc1 주요 JSONL 하나에 Goal·통합·완료 판정이 담기게 하고, 보조 로그는 출처를 구분해 선택 ZIP에 넣는 방향으로 준비합니다. 주요 파일을 인위적으로 합쳐 원래 하나의 세션인 것처럼 만들지 않습니다.

## 4. 데모에서 기억하게 할 장면

| 장면 | 사용자 가치 | 어떤 점수 근거와 연결되는가 |
|---|---|---|
| 도착 실적 없음 | 잘못된 확답을 피하고 확인 대상을 즉시 앎 | 검증 범위·실패 대응·완료 상태 |
| 주문/출고 차이 | 여러 화면을 오가지 않고 오출 근거를 찾음 | 결과 중심 목표·정량 비교 |
| 발화/원본 클릭 | AI 초안의 출처를 사람이 확인 가능 | 완료 확인 기준·신뢰할 수 있는 증거 |
| 모드 전환 | API/영상 장애에도 작업이 어디까지 가능한지 명확함 | 실행·실패 수정·한계 공개 |

최종 사용 의향을 얻으려면 '이 화면이 내 판단을 어떤 순서로 줄여주는가'가 보여야 합니다. 화려한 오프닝보다 30초 안에 미도착 사례의 판단 차이를 보여줍니다. 업무 효과 수치는 실제 비교 측정 결과만 사용합니다.

## 5. 5페이지·5분 구성

| 페이지 | 시간 | 화면·근거 |
|---|---:|---|
| 1 문제·목표 | 40초 | 상담 업무와 실측 기준; 예시 수치는 제거 |
| 2 실제 Goal·위임 | 50초 | 원문 핵심, 자율 판단 범위, 4PC 결과 책임 |
| 3 두 핵심 흐름 | 150초 | 미도착·오출 실제 시연과 근거 드릴다운 |
| 4 검증·실패 수정 | 40초 | 분모 있는 평가 결과, 결함/수정/재검증 사례 |
| 5 성과·한계·사용 | 20초 | 실제 효과, replay/live 범위, 재현 링크 |

질의응답 3분에는 '왜 규칙만으로 하지 않았나', '실제 데이터인가', 'AI가 확신해도 근거가 없으면?', '운영 도입에 무엇이 남았나', '실제 자동 수행 범위는?'을 준비합니다. 우리 구현에 없는 기능을 전망 설명과 섞지 않습니다.

## 6. 내부 검토표와 우선순위

검토자는 각 행을 **충분 / 보완 / 미확인**으로 판정하고 파일·행·화면·로그 위치를 붙입니다. 공식 점수를 예측하는 숫자표로 쓰지 않습니다.

- [ ] 실제 Goal 원문이 주요 세션에 있으며 결과와 완료 조건이 연결된다.
- [ ] 에이전트의 자율 판단 범위와 사람이 개입한 이유를 설명할 수 있다.
- [ ] 두 경로가 실제 통합된 상태로 시연된다.
- [ ] 실패·수정·재검증의 원본 근거가 하나 이상의 사례로 연결된다.
- [ ] 로그 수치의 의미·중복·미완료·비용 미확인을 구분한다.
- [ ] 합성 데이터·replay/live·실측/예시 구분이 화면과 발표에 일치한다.
- [ ] 최대 5페이지·5분/3분·링크 접근·9/22 12시 마감을 지킨다.

시간이 모자라면 P1 확장·통계·새 디자인 장식을 먼저 줄입니다. Goal/실제 로그/핵심 검증/제출 확인을 마지막까지 남깁니다. 점수 전략 검토는 Q04, 발표 반영은 D01, 제출 최종 확인은 U02가 맡습니다.
