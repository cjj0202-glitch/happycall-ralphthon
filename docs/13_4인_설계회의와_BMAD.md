# 4인 설계회의 — BMAD·Grill-me·Ralph 적용

**현재 적용:** DEC-013~015와 [통합 프롬프트](../PROMPT_team.md)가 이후 사용자 결정을 반영합니다. 로컬 구현은 착수됐고 live AI는 이번 범위에 포함됩니다. Playwright를 우선하되 실제 사람 검증은 미완료입니다. 아래 최초 회의 계획을 미실행 단계 전체의 착수 차단으로 재적용하지 않습니다.

2026-09-21 사용자 요청: 네 사람이 논의하면서 하나의 큰 솔루션을 설계하고, 설계·검증 후 각 PC에 일을 하나씩 배정한다. 최초 용어 확인에서 사용자는 **BMAD**를 선택했고, 이후 교육의 **First Bolt** 자료도 별도로 반영해 달라고 했다. 둘은 같은 방법이 아니다. 이 문서는 우리 팀에 맞춘 운영안이며, BMAD/Grill-me 패키지를 설치하거나 실행했다는 뜻이 아니다.

## 1. 방법을 어디에 쓰는가

| 방법 | 참고한 원칙 | 우리 적용 | 결과물 |
|---|---|---|---|
| BMAD | 제품 의도·요구사항·UX·공유 구조·스토리를 연결하고 필요한 정도만 계획 | 사업/사용자/기술/검증 관점으로 설계 검토, 기존 문서를 확장 | docs/03·04, 기술 결정카드, P02 계약, TODO |
| Grill-me | 선행 결정부터 질문하고 추천안·근거를 제시해 숨은 가정 발견 | 핵심 질문 하나씩. 사실은 저장소에서 조사하고 사람이 가치·범위를 결정 | 질문 트리, 결정 기록, 미해결 사항 |
| FDE First Bolt | 전체 여정 중 병목 하나를 작은 실험으로 확인 | 실제 사람이 쓴 관찰을 바탕으로 중요한 변화 하나씩 재시험 | UX01~03 실험 카드·관찰·Handoff |
| Shape Up | 일정에 맞춰 범위를 조절 | 큰 솔루션 지도는 유지하고 행사에서 검증할 두 흐름을 우선 완성 | 이번/다음/장기 범위와 제외 이유 |
| Ralph | 작은 작업을 실행·검증하고 다음 실행에 남길 기록 보존 | 설계 확정 후 PC당 DOING+REVIEW 하나, pc1 인수 후 체크 | 커밋, 기대/실측, 증거, DONE |

BMAD 원문: [계획 경로](https://docs.bmad-method.org/plan/choose-a-planning-path/), [요구사항과 명세](https://docs.bmad-method.org/plan/define-requirements-and-a-specification/), [UX와 구조](https://docs.bmad-method.org/plan/design-ux-and-architecture/), [다관점 토론](https://docs.bmad-method.org/customize/run-multi-agent-discussions/). 큰 작업도 작은 실행 단위로 나누고, 여러 구현자가 공유할 판단을 문서에 남긴다는 점을 참고했다. 위 표의 4인 회의·시간 배분·작업 ID는 **우리 팀의 적용안**이다.

Grill-me 원문: [진입 스킬](https://github.com/mattpocock/skills/blob/main/skills/productivity/grill-me/SKILL.md), [실제 grilling 지침](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md). 현재 진입 파일은 grilling을 호출하며, 실제 지침은 선행 결정이 해결된 질문들을 라운드로 묶는다. 우리는 사용자의 '하나씩 설계' 요청에 맞춰 핵심 질문 하나를 기본으로 하고, 서로 독립인 확인만 최대 3개로 묶는다. 특정 슬래시 명령이 이 PC에서 동작한다고 가정하지 않는다.

공개 원문 재확인일은 2026-09-21이다. 외부 프로젝트의 명령·문서 이름은 참고 정보이며 우리 저장소의 명령으로 사용하지 않는다. 교육 자료 캡처 대조와 팀 적용은 [16](16_FDE_First_Bolt_적용.md)에 분리했다.

## 2. 사람과 AI의 책임

네 사람의 이름·역할은 아직 미등록이다. 아래는 회의 관점이며 PC 구현 역할과 반드시 같을 필요는 없다. 각 회의 시작에 실제 담당자를 확인한다.

| 관점 | 확인할 질문 | 맡을 사람 |
|---|---|---|
| 업무·가치 | 누가 어떤 업무를 끝내며 무엇이 개선되는가 | 미정 |
| 사용자 경험 | 처음 보는 사람이 어떤 순서로 무엇을 누르는가 | 미정 |
| 기술·데이터 | 어떤 근거·상태·계약으로 구현하고 합치는가 | 미정 |
| 검증·심사 | 무엇을 재현하면 주장과 배점을 뒷받침하는가 | 미정 |

AI는 진행자·조사자·기록자다. 여러 관점의 검토 의견을 낼 수 있지만 네 사람의 발언이나 동의를 대신 만들지 않는다. 'AI 검토 의견'과 '사람 발언'을 따로 기록한다. BMAD의 다관점 토론을 실제 네 사람의 합의나 독립된 실험 결과로 표현하지 않는다.

결정권자는 첫 회의에서 지정한다. 기본 제안은 대표 1명이 결정 책임을 지고, 나머지 3명 의견과 반대 이유를 남기는 방식이다. 참석하지 않은 사람은 미응답으로 남긴다. 영향받는 담당자의 확인이 없으면 관련 구현을 시작하지 않고, 독립적인 준비·조사는 계속한다. 안전·데이터 정합성 문제를 다수결로 덮지 않는다.

회의는 대면 통화 또는 단체 채팅으로 진행할 수 있다. 같은 질문 카드를 네 사람에게 보여주고 각자의 선택·이유·우려를 받은 뒤 AI가 공통점과 이견을 요약한다. 비동기 회의라면 결정 시각과 미응답자를 남긴다. 다른 세션의 AI가 작성한 제안만 도착한 경우에는 그 제안을 사람의 승인으로 기록하지 않는다.

사용자가 허용한 병렬 에이전트 작업은 독립적인 사실 조사·초안 검토·검사에 쓴다. 하나의 세션에서 여러 관점을 연기한 결과, 실제 분리 에이전트의 검토, 실제 사람 네 명의 의견을 각각 구분한다. 병렬 조사 중에도 그 결과에 의존하지 않는 질문은 진행하되, 담당 경로가 겹치는 파일은 동시에 편집하지 않는다.

## 3. 큰 솔루션과 행사 범위를 함께 관리

전체 후보 구조는 [솔루션 지도](../planning/solution-map.md), 기능별 판단은 [기능 검토표](../planning/features.md)다. 기존 docs/03·04는 논의를 시작할 설계 기준선이다. 이름·주사용자·두 시나리오를 네 사람이 최종 합의한 것으로 소급하지 않는다.

- **전체 비전:** 접수, 근거 조회, 판단 지원, 사람 확인, 처리 이력, 개선 분석이 연결되는 해피콜 업무 솔루션.
- **행사 결과:** 그 비전의 핵심을 미도착·오출 두 경로로 실제 보여주고 반복 검증한다.
- **후속 제품:** 운영 시스템 연결, 권한·감사, 실제 처리 승인, SLA·통계, 새 유형을 필요한 근거와 함께 확장한다.

확장은 Case/Intake/Evidence/Decision/Action/History/Media 계약을 공유하는 방향으로 검토한다. 처음부터 별도 서비스 8개를 만드는 결론은 아니다. 배포 단위와 저장소 수는 B03에서 비용·시간·통합 위험을 비교해 결정한다.

## 4. 순서와 종료 조건

첫 세션은 현재 상태를 확인하고 **B01의 첫 질문만** 시작한다. 아래 시간은 회의 운영 예산의 제안이며 공식 시간표가 아니다. 이미 지난 시각을 앞으로의 일정처럼 사용하지 않는다.

최신 사용자 요청에 따라 **지금의 기본 경로는 15~20분 안에 핵심 사용자·이번 범위·첫 Bolt를 정하는 짧은 회의**다. 아래 상세 회의는 필요한 부분만 펼치며, 미해결 결정은 그대로 남긴다. 개발 단계의 Astra Ultra 사용 요청은 인수인계에 전달하고 현재 간단 정리를 모델 변경 완료로 표현하지 않는다.

| 단계 | 핵심 논의 | 종료 증거 | 작업 |
|---|---|---|---|
| 0 현황 정리, 10분 | 규정·기존 자산·현재 시각·4명 참석/준비 상태 | 사실/제안/미확인 표 | S01 기록 재사용 |
| 1 문제와 성공, 20분 | 주사용자·대표 문의·업무 시작/종료·현재 문제·측정 목표 | 네 사람 의견과 결정권자가 있는 제품 브리프 | B01 |
| 2 사용자 흐름과 기능, 25분 | 정상 흐름·실패 흐름·무엇을 이번에 넣고 뺄지 | 기능별 이유·우선순위·검증·후속 경계 | B02 |
| 3 데이터/구조, 25분 | 실제 킷 키·null·상태·API·미디어·UI·배포 경계 | 계약 샘플·정답 fixture·구조 결정 | P02·B03 |
| 4 인수 조건, 15분 | 설계 간 충돌·필수 조건·준비·실험 가설·남은 차단 사항 | 계약·실험 계획의 P03 검토와 G02 시작 판단 | P03·G02 |
| 5 작은 사용자 실험 | 실제 Goal 시작 후 병목 하나를 구현하고 관찰→한 가지 수정→재시험 | 실제 사람의 관찰과 변경 근거, 설계에 반영한 Handoff | L01·S02·UX01~03 |
| 6 확장 실행 | 확인한 경계 안에서 한 덩어리 배정→구현→검증→통합 | 증거를 대조한 DONE | 기존 제품 TODO |

문서만 생성됐다고 회의가 완료되는 것은 아니다. B01~B03을 TODO로 두고 실제 대화·선택·반대·근거를 채운 뒤 검증한다. 중요한 결정이 미해결이면 그 결정에 의존하는 단계만 대기한다.

P03/G02 시점의 설계 검토는 실제 사용성 검증 완료를 뜻하지 않는다. UX01~03의 결과로 바뀐 화면·계약·수용 기준을 반영한 후 해당 화면 확장을 배정한다. UX 결과에 의존하지 않는 미디어·데이터 준비는 정해진 소유 경로에서 병행할 수 있다. 교육 스크린샷 대조 SRC01의 증거는 출처 확보·문서 반영을 확인하며, 실제 Bolt 실험 완료 증거와 구분한다.

## 5. 한 질문의 진행 방식

1. **질문:** 지금 확정해야 할 선택 하나와 선행 결정.
2. **자료:** 저장소·공식 안내에서 확인한 사실, 가정, 미확인 항목을 구분.
3. **선택:** 2~3개 대안과 추천안. 업무 효과·시연·개발 시간·의존성·위험을 비교.
4. **사람 의견:** 네 사람의 실제 의견을 수집. 한 사람이 전달했다면 전달자와 출처를 기록.
5. **반대 검토:** 추천안이 실패하는 조건을 한 번 확인. 사실 질문은 AI가 조사.
6. **결정:** 채택/기각/보류, 결정자·이유·다시 열 조건을 기록.
7. **반영:** 관련 설계·기능표·작업 의존성을 갱신하고 다음 질문 하나를 제시.

질문은 결정에 필요한 정보를 얻으면 끝낸다. 이미 근거가 충분한 선택을 같은 표현으로 반복 질문하지 않는다. 반대로 사람의 답이 필요한 선택을 응답 없이 시간이 지났다는 이유로 합의 처리하지 않는다. 관찰이 필요한 쟁점은 토론으로 확정하지 않고 담당·작은 실험·재논의 조건을 지정한다.

기록은 [회의 템플릿](../planning/meeting-template.md)과 [결정 대장](../planning/decisions.md)을 쓴다. 회의 메모는 `planning/meetings/날짜-주제.md`에 새로 만든다. 원문 전체를 보관하기보다 결정에 필요한 발언·근거를 남긴다. 민감한 회사 자료나 원본 대화 로그는 넣지 않는다.

| 분기 | 먼저 풀 질문 | 뒤따르는 질문 |
|---|---|---|
| 사용자 | 첫 사용자는 상담 담당자인가 | 사용 장소·입력·업무 권한·센터와의 인계 |
| 가치 | 한 건을 처리했다는 종료 상태는 무엇인가 | 시간 측정 시작/끝·오류 비용·비교 기준 |

| 범위 | 해커톤에서 반드시 작동할 경로는 무엇인가 | P0/P1/후속, 빼도 핵심 가치가 유지되는가 |
| 입력 | 음성/텍스트/선택 중 어떤 경로를 먼저 제공하는가 | 수동 수정·출처·오인식·빈 입력 |
| 근거 | 어떤 원본 키와 시각을 보여줘야 신뢰할 수 있는가 | 계획/실적 구분·다른 점포·다른 토트 차단 |
| 판단 | 확정 사실과 확인 필요를 어떻게 나누는가 | 상태 전이·확인 권한·충돌 처리 |
| 조치 | 자동 초안과 사람이 해야 할 일의 경계는 무엇인가 | 저장·이관·재시도·중복·실제 쓰기 제외 |
| 구조 | 따로 만드는 3개 모듈이 무엇을 공유해야 하는가 | 계약 버전·컴포넌트·상태·오류·소유 경로 |
| AI | 제품 내부 live API가 이번 결과에 필요한가 | 권한·예산·정확도·실패 대체·모드 표시 |
| 검증 | 어떤 반례가 있으면 실패로 판정할 것인가 | 20입력·12경계·2흐름×3·오프라인·평가 누수 |
| 제출 | 발표의 각 주장에 어떤 실행 증거가 연결되는가 | 실제 Goal·JSONL·시연·영상·자료·제출 수신 확인 |
| 확장 | 다음 업무 유형을 넣을 때 무엇만 추가하면 되는가 | 플러그인 경계·연동 adapter·승인·운영 지표 |

## 7. 기능 채택 기준

각 기능은 대상 사용자/문제, 기대 결과, 근거, 현재 데이터, 화면, 계약, 의존성, 담당, 크기, 검증, 이번/후속, 채택 이유를 갖춘다. '있으면 멋짐'만으로 P0에 넣지 않는다.

우선순위 비교 축은 사용자 효과·공식 평가 증거·시간 내 재현 가능성·의존성·실패 비용이다. 점수를 매긴다면 그 값은 **팀 내부 추정치**이며 공식 심사 점수가 아니다. 자료가 부족하면 숫자 대신 모름으로 표시한다. 후보를 뺄 때에도 이유와 재검토 조건을 보존한다.

P0 추가는 동등한 시간의 다른 범위를 줄이거나 남은 일정 안에서 끝낼 근거를 제시한다. DEC-011·013으로 제품 내부 실제 STT/GPT는 이번 필수 범위다. 개발 자동검사는 replay로 수행하고 승인된 데모 정책·예산에서 실제 시연을 검증한다. 실제 Astra Goal과 로그 보존은 별도 제출 준비다.

## 8. 네 PC에 넘기는 작업 카드

배정 전에 작업 ID, 현재 설계 커밋, 목표 결과, 편집 경로, 선행 산출물, 예제 입력/출력, 수용 기준, 제외 범위, 검증 명령, 결과 파일, 막힐 때 기준을 한 카드에 쓴다. 역할 이름만 주고 '알아서 만들어'라고 배정하지 않는다.

최초 역할은 pc1 통합/계약/검증, pc2 미디어, pc3 근거 UI, pc4 접수/판정 **제안**이다. 사람·hostname·GitHub·준비 실측 후 확정한다. 각자 task branch에서 만들고 pc1이 커밋을 가져와 실제 통합 검사한다. 공유 문서와 중앙표는 pc1이 관리한다.

## 9. 변경과 회의 종료

기능 변경 제안은 '문제→대안→영향받는 계약/화면/테스트→일정 영향→추천→결정자' 순서로 남긴다. 합의 뒤 기존 문서를 직접 갱신해 서로 다른 정본을 만들지 않는다. DONE 산출물을 바꾸면 재검증 또는 후속 작업을 둔다.

회의 종료 시 진행자가 **이번에 결정한 것 / 남은 것 / 다음 질문 하나 / 담당별 다음 행동 / 기준 커밋**을 남긴다. Vercel은 사용자 재개 요청 전까지 보류한다. 회의가 길어져도 제출 마감 9/22 12:00을 임의로 늦추지 않는다.
