# 랄프톤 운영 설계 — 노트북 4대로 해피콜 시스템 만들기

> 랄프(Ralph) = 에이전트에게 **같은 프롬프트를 계속 물려** 스스로 다음 할 일을 찾게 하는 방식.
> 사람이 매번 지시하지 않는 대신, **무엇을 끝났다고 볼 것인가**를 먼저 정해 둬야 합니다.

---

## 1. 구조 — 허브 앤 스포크

```
                    ┌─────────────┐
                    │   pc1 main  │  지시를 만드는 것은 여기뿐
                    │ 오케스트레이터 │  통합 · 판정 · 발표
                    └──────┬──────┘
          ┌────────────────┼────────────────┐
          │                │                │
    ┌─────▼─────┐    ┌─────▼─────┐    ┌─────▼─────┐
    │    pc2    │    │    pc3    │    │    pc4    │
    │   (미정)   │    │   (미정)   │    │   (미정)   │
    └───────────┘    └───────────┘    └───────────┘

          편지는 전부 GitHub Issues 를 지나간다
```

### 🚨 워커끼리 직접 지시하지 않는다

pc2 가 pc3 에게 직접 일을 시키면 **누가 무엇을 맡았는지 아무도 모르게** 됩니다.
원본 채널에서 중계 세션을 둔 날, 그 세션이 받은 24통 중 6통(25%)이 남의 건이었고
담당을 찾느라 5회를 질의했으며, 중계 중 판정을 옮기다 틀려 **화면이 30분간 옛 문구를
내보냈습니다.** 처방은 「조심하자」가 아니라 **중계할 자리를 없애는 것**이었습니다.

워커가 다른 워커의 산출물이 필요하면 → **메인에게 요청**합니다(유형 C).

## 2. 역할 배정 — 아직 비어 있음

`channel/pcs.json` 의 `role` 을 채우면 라벨·보드·템플릿이 전부 따라옵니다.
정할 때 기준 하나만 지키십시오.

> **한 PC 의 산출물이 다른 PC 의 입력이 되는 지점을 최소화합니다.**
> 랄프 루프는 기다리는 것을 못 합니다. 막히면 헛돕니다.

배정 후보(해피콜 시스템 기준):

| 슬롯 | 후보 역할 | 산출물 | 남에게 주는 의존 |
|---|---|---|---|
| pc1 | 메인 — 오케스트레이터 | 합성 데이터, 통합, 발표 | 데이터를 모두에게 (**먼저 만들어야 함**) |
| pc2 | 영상 | CCTV·데모 영상 파일 | wms 가 재생할 파일 |
| pc3 | WMS 화면 | SPA — 클릭하면 영상 재생 | 없음(영상은 플레이스홀더로 먼저) |
| pc4 | 해피콜 엔진 | 통화 음성·전사·응대 판정 | wms 가 띄울 접수서 |

🚨 **의존을 끊는 법**: 받는 쪽이 먼저 **더미**로 인터페이스를 고정합니다.
pc3 는 영상이 없어도 `demo/video/placeholder.mp4` 로 화면을 완성해 두고,
pc2 의 진짜 파일이 오면 **파일만 갈아 끼웁니다.** 인터페이스 계약은 유형 D 편지로 못 박습니다.

## 3. 루프 규율 — 🚨 폴링이 편지를 부른다

원본 실측: 감시(폴링) 세션을 켠 날 편지가 **6.4통/h → 25.3통/h (4배)** 로 뛰었습니다.
교란요인이 통제되지 않아 인과로 단정할 수는 없지만, 방향은 분명합니다.

랄프 루프는 **폴링 그 자체**입니다. 그대로 두면 4대가 서로에게 편지를 쏟아붓습니다.

🎯 **다시 보면 터진 것은 «읽는 폴링»이 아닙니다.** 그 감시 세션이 **중계 허브**가 되어
남의 건까지 받아 옮기면서 편지를 만들어냈습니다. 그래서 처방은 「폴링하지 마라」가 아니라
**「감시기는 읽기만 하고, 중계하지 마라」** 입니다.

### 감시기 — 별도 터미널에서 계속 돈다

```bash
python channel/mail.py watch --interval 30 --bell
```

🚨 **새 편지·회신·종결이 있을 때만 출력합니다.** 변화가 없으면 아무 말도 하지 않습니다.
매번 「없음」을 찍으면 로그가 노이즈로 덮여 진짜 신호가 묻힙니다.

네트워크가 끊겨도 죽지 않습니다 — 간격을 늘려 가며 재시도합니다.

### 각 워커의 1회 루프

```
1. 할 일이 있으면 → 한다                     ← 기본. 여기에 시간을 쓴다
2. 감시기가 울렸거나 한 덩어리를 끝냈으면 → inbox 확인
3. 상태를 갱신한다                            ← 편지가 아니다. body 덮어쓰기
4. 다시 1
```

| 규율 | 값 | 왜 |
|---|---|---|
| 감지 | **감시기 30초** (별도 터미널) | 읽기만 하므로 편지를 부르지 않는다 |
| 루프 안 inbox 호출 | **하지 않는다** — 감시기가 울렸을 때만 | 반복 호출은 루프를 느리게 하고 진전을 막는다 |
| 🚨 중계 | **하지 않는다** | 남의 건을 받아 옮기는 자리가 편지를 4배로 만들었다 |
| 상태 갱신 | 한 덩어리 끝날 때마다 | 낡은 상태는 거짓이다 |
| 편지 보내기 | **A·C·D·E·F 만** | B(상태)·G(신호)·H(검증)는 편지가 아니다 |
| 메인의 지시 | 한 번에 **한 덩어리**씩 | 큰 덩어리를 주면 워커가 중간에 길을 잃는다 |

### 🚨 「막혔다」를 편지로 만들기 전에

원본 금기 4 — **내 세션에서 막힌 일을 남에게 시키지 않습니다.** 권한 세탁입니다.
막혔으면 ① 스스로 30분 ② 그래도 막히면 **사람에게** 올립니다. 다른 워커에게 넘기지 않습니다.

## 4. 붙여넣는 랄프 루프 프롬프트

각 워커 노트북에서 **작업 폴더 안에서** 시작합니다. Codex CLI 기준이며 Claude Code 도 같습니다.

```
이 레포의 AGENTS.md 를 먼저 읽고 그대로 따르라.

너는 <슬롯>이다. 먼저 `python channel/whoami.py` 로 신원을 확인하고,
「미등록」이 나오면 거기서 멈추고 나에게 보고하라.

별도 터미널에서 `python channel/mail.py watch --interval 30 --bell` 을 띄워 두었다.
새 편지가 오면 그쪽이 울린다. 루프 안에서 inbox 를 반복 호출하지 마라.

그 다음부터 아래를 반복하라.

  1. 지금 맡은 덩어리가 있으면 그것을 끝낸다.
  2. 끝냈거나 막혔거나 감시기가 울렸으면 `python channel/mail.py inbox` 로 편지를 본다.
     - 편지가 있으면 read 하고, 6칸 중 「검증 방법 + 기대값」을 먼저 읽는다.
     - 그 기대값을 만족시키지 못하면 done 하지 않는다. 회신으로 막힌 지점을 적는다.
  3. `python channel/mail.py status --set "<지금 하는 일 한 줄>"` 로 상태를 갱신한다.
  4. 1 로 돌아간다.

규칙:
- 상태 보고를 편지(이슈)로 만들지 마라. status --set 만 쓴다.
- 다른 워커에게 직접 지시하지 마라. 필요하면 pc1(메인)에게 요청한다.
- 「에러 없음」을 검증이라고 쓰지 마라. 수치와 시각을 적는다.
- 인용할 때 「그쪽」이라고 쓰지 마라. 슬롯명으로 적는다.
- 시크릿 값을 편지에 넣지 마라. 경로만 적는다.
- 30분 막히면 루프를 멈추고 사람에게 올려라.
- 남의 앞으로 온 편지를 대신 처리하거나 옮기지 마라(중계 금지).
```

메인(pc1)은 루프 대신 **지시를 만들고 판정**합니다.

```
너는 pc1(메인)이다. AGENTS.md 를 따르라.

  1. `python channel/mail.py board` 로 4대 상태를 본다.
  2. 멈춰 있는 워커가 있으면 다음 덩어리를 편지로 보낸다.
     제목은 결론 한 줄. 본문은 6칸 템플릿. 기대값을 반드시 적는다.
  3. 회신이 온 편지는 기대값 대조로 판정한다. 통과면 done, 아니면 근거를 적어 되돌린다.
  4. 1 로 돌아간다. 감시기가 울릴 때, 또는 최소 10분 간격.
```

## 5. 산출물이 어디로 가는가

| 무엇 | 어디 | 명령 |
|---|---|---|
| 코드·설계·규칙 | 이 레포 | `git push` |
| 영상·음성(큰 파일) | **Release 자산** | `gh release upload demo-assets 파일.mp4 --clobber` |
| 받기 | | `gh release download demo-assets -p '*.mp4' -D demo/video/` |
| 시크릿 | 각 PC 로컬 `.env` | 레포·이슈 어디에도 올리지 않는다 |

🚨 영상을 레포에 커밋하지 마십시오. 100MB 제한에 걸리고, 걸리지 않아도 4대가
clone 할 때마다 그 용량을 받습니다. `.gitignore` 가 `*.mp4`·`*.wav` 를 이미 막습니다.

## 6. 네트워크가 끊기면

행사장 와이파이는 끊깁니다 — **이 킷을 세팅하는 날에도 실제로 끊겼습니다.**
Issues 는 네트워크가 있어야 하므로 대체 경로를 미리 정해 둡니다.

| 상황 | 대체 |
|---|---|
| 잠깐 끊김 | 작업을 계속한다. 편지는 복구 후 한 번에 보낸다. **루프를 멈추지 않는다** |
| 오래 끊김 | 메인이 **말로** 지시한다. 복구 후 결정사항만 유형 D 편지로 남긴다 |
| 끝까지 안 됨 | USB 로 산출물을 모은다. 통합은 메인 노트북에서 한다 |

🚨 **끊겼을 때 가장 위험한 것은 「보냈는데 조용하다」를 「상대가 안 한다」로 읽는 것입니다.**
`gh` 가 실패했는지부터 확인하십시오.

## 7. 체크포인트 — 무엇을 버릴지 미리 정한다

시간이 부족하면 아래 순서로 버립니다. 미리 정해 두면 새벽에 다투지 않습니다.

1. 관리자 통계 화면
2. 시나리오 수 축소 (4건 → 2건)
3. 실시간 생성 → 미리 만든 파일로 대체
4. 예쁜 화면
5. **핵심 경로 한 줄기** ← 이건 마지막까지 지킨다

핵심 경로 한 줄기 = 「해피콜 접수 → WMS 화면에서 클릭 → 근거 영상이 뜬다」.
이것이 3회 연속 같은 결과로 돌면 시연할 수 있는 상태입니다.
