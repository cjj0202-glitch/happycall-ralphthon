## 2. 개념별 적용 지도

다음 설명은 교육 캡처와 브리핑의 요지를 우리 제품에 맞춰 풀어 쓴 것이다. BMAD는 설계·실행의 구조, Grill-me는 질문 방식, Bolt는 학습 실험 단위, Ralph는 구현 반복으로 역할을 나눈다. Bolt.new 서비스와도 구분한다. 사용자에게 교육의 '기존 PoV를 다시 쓰지 않는다'를 그대로 적용하지 않는다. 해커톤에서는 기존 설계를 B01의 출발점으로 쓰고, 실제 네 사람이 무엇을 유지·변경할지 결정한다.

| 개념 | 참고한 의미 | 우리 팀에서 하는 일 | 기록 |
|---|---|---|---|
| PoV | 누구의 어떤 필요·문제인가 | 기존 해피콜 문제를 B01에서 확인하고 가정 표시 | 제품 브리프 |
| HMW | 문제를 풀 수 있는 기회 질문 | 담당자가 문의 한 건의 근거와 다음 조치를 함께 이해하게 하는 방법 토론 | B01 회의 |
| PRD 가설 | 사용자·범위·성공 조건을 짧게 연결 | docs/03의 목표와 기능별 검증을 합의 | docs/03·기능표 |
| User Journey | 제품 밖까지 이어지는 경험 | 문의 발생·접수·확인·센터 협업·답변·후속 업무를 그림 | B02 솔루션 지도 |
| User Flow | 제품 안의 화면·행동·상태 | 입력→근거→판단→사람 확인의 정상/실패 경로 | docs/04 |

| Subtractive Design | 병목과 무관한 요소를 덜기 | 첫 실험에서 통계/설정/부가 메뉴를 빼고 핵심 행동 관찰 | 포함/제외 목록 |

| Silent Test | 조작법 설명 없이 과업을 수행하게 관찰 | 실제 사람의 첫 행동·발견 시간·멈춤·오클릭·완료 기록 | UX01/02/03 |

ICE는 여기서 교육의 **학습 목적**으로 사용한다. Confidence가 낮은 병목을 시험한다는 안내를, 높은 확신에 점수를 주는 다른 우선순위 산식과 섞지 않는다. 고정된 곱셈 공식이나 공식 해커톤 배점은 도입하지 않는다. 확신이 낮다는 이유로 위험한 기능을 운영에 배포하는 것도 아니다.

### 상위 7단계 루프와 10단계 실행 과정

캡처 p02의 상위 루프는 PoV→HMW→PRD v0→Single CTA→Mockup v0→Silent Test→Mockup v1이다. p03~p04의 다음 10단계는 이를 구체적인 행동으로 풀어 쓴 별도 도식이다. 둘을 서로 모순된 단계 수로 처리하지 않는다.

| 교육의 10단계 | 우리 팀에서 남길 판단·증거 | 연결 |
|---|---|---|
| 1 살펴보기 | 제품 밖 여정과 어디서 막히는지 사실·가정 구분 | B01/B02 |
| 2 정의하기 | 실제 사용자의 상황·필요·해결 기회 확인 | B01 |
| 3 초점 정하기 | 가치·학습·작은 구현 가능성으로 병목 하나 선택 | B02 |
| 4 기획하기 | 기대 행동과 포함·제외·성공 조건을 한 장으로 압축 | B02·Bolt 카드 |
| 5 설계하기 | 가설을 시험할 만큼의 정밀도·주행동·상태 정의 | B03·UX01 |
| 6 구현하기 | 설명 없이 눌러볼 수 있는 작은 작동 화면 | UX01 |
| 7 덜어내기 | 선택한 과업을 방해하는 요소와 제거 이유 기록 | UX01 |
| 8 사용해보기 | 실제 사람의 행동·막힘과 이벤트 기록 | UX01 |
| 9 개선하기 | 관찰로 확인한 중요한 변화 하나를 만들고 재시험 | UX02 |
| 10 이어가기 | 다음 질문·남은 문제·개발 입력을 전달 | UX03·Handoff |

이 흐름은 일방향 통과 절차가 아니다. 화면을 보니 예상 행동이 성립하지 않으면 PRD를, 사람의 막힘이 문제 가정을 반박하면 PoV/HMW를 다시 검토한다. 영향받는 결정·계약·작업을 함께 갱신한다. 교육의 '4시간 한 사이클·첫 화면 30분'은 시간 제한의 예시이며 해커톤의 고정 규칙으로 가져오지 않는다.

교육의 Two-way Door는 되돌릴 수 있는 작은 변화를 빠르게 시험하자는 관점으로 적용한다. 문구·배치 실험은 정해진 소유 경로에서 진행할 수 있다. 외부 공개·실 시스템 쓰기처럼 되돌리기 어려운 One-way Door는 영향·권한·복구 조건을 먼저 확인한다. 이것이 사용자 지시나 저장소 권한을 확대하지는 않는다.

참조 스튜디오의 Gateway v1 기능 정리→v2 사용자별 복구→v3 상태 시뮬레이션과 복잡도→v4 상태별 주행동 정리는 **강의에 실린 사례**다. 우리 제품의 수행 결과가 아니며 Gateway를 복제하지 않는다. 기능을 추가한 이유와 덜어낸 이유를 모두 기록하는 방식만 참고한다.

## 3. First Bolt 후보 — 아직 팀 미결정

| 후보 | 사용자의 병목 가설 | 배우려는 것 | 실험 크기 | 초기 추천 |
|---|---|---|---|---|
| A 근거 누락→확인 요청 | 계획과 도착 기록을 혼동해 확정 답변 | null을 보고 '미도착 확정' 대신 확인 요청을 선택하는가 | 합성 케이스1·화면1·상태5개 | 추천 |
| B 발화→접수 수정 | 추출 필드가 틀려도 출처를 못 찾음 | 출처를 열어 수량/상품을 고칠 수 있는가 | 합성 발화1·접수폼1 | 대안 |
| C 영상→관련성 이해 | 다른 영상도 이 케이스 증거로 믿음 | 토트/시각 불일치를 알아차리는가 | 관련/무관 샘플2개 | 대안 |

A를 추천하는 이유는 현재 제품 차별점인 '근거와 미확인 구분'을 작게 시험하고, 기존 CASE-0001의 누락 데이터로 검증하기 쉽기 때문이다. 사용자가 실제로 혼동하는지는 **미측정 가설**이다. 네 사람이 B02에서 후보를 결정한다.

First Bolt의 '첫'은 Journey의 첫 번째 단계라는 뜻이 아니다. 끝부분의 근거 해석이 가장 큰 병목이면 그 지점부터 실험할 수 있다.

가설 예시: 합성 미도착 문의를 처리하는 상담 담당자가 근거 누락을 이해하고 확인 요청을 선택하는 데 막힌다고 가정한다. 도착 계획과 실적을 분리하고 주행동을 표시한 화면으로, 설명 없이 확인 필요 상태와 다음 행동을 찾는지 시험한다. 기간·참가자·성공 기준은 실행 전에 고정한다.

## 4. 실험 계약

First Bolt의 초깃값 제안이며 실제 테스트 전에 팀이 결정한다.

- 과업: '이 문의에서 확인된 것과 추가 확인할 것을 살펴보고, 다음 담당자에게 보낼 내용을 준비해 주세요.' 버튼 위치나 올바른 결론은 미리 말하지 않는다.
- 참가자: 다른 팀원 중 2명 이상을 대상으로 시작하고 역할·경험을 기록한다. 실제 업무 담당자 참여가 없으면 '팀 내부 사용성 관찰'로 표시한다.
- 관측: 첫 행동, 주행동 발견 시간(3초 목표), 첫 올바른 클릭 시간, 멈춤 위치·시간, 잘못된 클릭, 반복 클릭, 도움 요청, 과업 완료, 실제 미도착으로 단정했는지. 화면이 준비된 시점을 0초로 하고, '발견'으로 인정할 행동을 사전에 정해 발견과 클릭을 혼동하지 않는다. 3초는 교육의 점검 관점을 적용한 목표이며 공식 심사 통과선이 아니다.
- 기준 고정: 실행 전에 참가자 수, 과업 완료의 종료 상태, 시간 한도, 도움 허용 여부, 잘못된 확정의 판정 예를 카드에 적는다. 측정 후 기준을 바꾸어 실패를 성공으로 바꾸지 않는다.
- 판정: 참가자별 원자료를 남긴다. 소표본 2명의 성공을 실제 현장 전체의 효과나 통계적 유의성으로 표현하지 않는다.
- 분리: '두 번 눌렀다'는 관찰, '처리 상태가 안 보여서 그랬다'는 해석이다. AI의 HTML 분석은 실제 관찰을 대신하지 않는다.
- Second Bolt: 관찰상 가장 큰 문제 하나만 바꾸고 같은 과업·조건으로 다시 본다. 반복 참여자의 학습 효과를 기록한다.
- Third Bolt: 남은 중요 문제를 반영하고 실제 사람이 다시 사용한다. 가능하면 업무 담당자가 참여한다. 팀원만 참여했거나 같은 참가자가 반복했다면 대상과 학습 효과를 표시하고 현장 사용자 검증으로 확대해서 쓰지 않는다.
- 결과: 성공 여부에 상관없이 무엇을 예상했고, 무엇을 봤고, 무엇을 바꿨는지 연결한다.

캡처 p06의 증거 3종은 별도로 수집한다. **관찰**에는 실제 행동을, **과업 후 인터뷰**에는 왜 그렇게 했는지·무엇을 기대했는지·불안·다음 사용 이유에 대한 사람의 답을, **이벤트 기록**에는 `screen_view → cta_click → task_complete → repeat_use`의 시각과 상태를 남긴다. 과업 중 조작법을 설명하지 않는 Silent Test와 과업 후 인터뷰는 충돌하지 않는다. 클릭 수만으로 가치가 입증되지 않으며 짧은 해커톤에서 실제 재사용을 보지 못하면 `repeat_use`는 미측정이다. 이벤트 로그에는 합성 케이스 식별자와 동작을 남기고 원본 대화·인증 값을 담지 않는다.

Build Quality는 계약·오류 복구·빌드·회귀 검증으로, Product Quality는 과업 완주·이해·신뢰·다음 업무 활용을 실제 사람에게 관찰해 확인한다. 기술 검사 통과를 사용자 가치 검증으로 대체하지 않는다. 화면이 그럴듯한 정도와 실제 작동 깊이를 구분해, 목업에서 재생하는 범위·실제 저장하는 범위를 기록한다.

## 5. 화면 상태별 설계 예시

| 상태 | 사용자에게 보여줄 것 | 주행동 제안 | 검사 |

| Empty | 문의 선택 전 설명·합성 표시 | 문의 선택 | 어디서 시작하는지 찾음 |
| Input | 선택한 문의·검토할 입력·필수값 | 근거 확인 | 빈 입력/틀린 케이스 방지 |
| Loading | 어떤 자료를 읽는지와 진행 상태 | 새 실행 비활성, 진행 상태 표시 | 중복 실행 방지·멈춤 구분 |
| Error | 실패한 근거·보존된 입력·복구 안내 | 다시 확인 또는 수동 검토 | 잘못된 성공·확정 차단 |
| Success | 확인된 사실·미확인·출처·다음 조치 | 확인 요청 초안 저장 | 사람 확인·이력·종료 이해 |

Primary CTA 하나라는 것은 보조 링크를 전부 없애거나, 모든 화면에 같은 버튼을 강제한다는 뜻이 아니다. 상태마다 중요한 다음 행동을 구분하는 원칙으로 적용한다.

5가지 상태는 모두 반드시 한 번씩 통과하는 순서가 아니다. 정상 경로는 Input→Loading→Success, 실패는 Loading→Error→Input/재시도로 갈린다. Success는 '조회·초안 준비가 끝남'일 수 있으며 문의의 사실관계나 배송 완료가 확정됐다는 의미와 분리한다. 네트워크 대기와 근거의 `missing/conflicting` 상태도 다른 축이다.

## 6. 산출물과 실행 시점

실제 구현은 설계·준비 G02와 L01 실제 개발 Goal 시작 뒤 진행한다. 작은 초기 화면을 S02 골격에 연결해 UX01→UX02→UX03을 수행한다. 그 후 관찰로 바뀐 설계·계약을 반영하고 근거/접수 화면 확장을 배정한다. P03/G02에서는 계약과 실험 계획을 검토하며, 아직 없는 사용자 관찰을 통과 증거로 쓰지 않는다. 병행 가능한 미디어·UI에 의존하지 않는 데이터 준비는 계약과 소유 경로에 따라 별도로 진행할 수 있다.

예정 산출물은 `experiments/bolt/1_bolt.md`, `1_bolt.html`, `1_test_result.md`, 이어서 2/3 버전과 `handoff.md`다. 교육 제출 저장소에 올리는 과제가 아니라 이 해커톤 저장소의 실험 기록이다. 아직 파일이 없고 실험을 하지 않았다는 상태를 유지한다.

Handoff에는 문제·여정·버전별 한 가지 변화·실제 관찰·남은 질문·FE 상태/CTA/이벤트·BE/API 데이터·권한·실패 복구·현재 커밋을 담는다. 버전이 증가했다는 사실만으로 개선됐다고 쓰지 않는다. 이 연결은 공식 완료 검증 증거에도 활용한다.

SRC01의 종료 조건은 확보한 PNG 11개의 사본 검증·분할 10장 확인 범위를 기록하고 브리핑의 누락을 이 문서에 반영하는 것이다. 10분할과 통짜 한 장은 같은 페이지의 사본이므로 서로 다른 강의 11개로 세지 않는다. 교육 자료 검토 완료가 사람의 회의나 실제 사용자 실험 완료를 뜻하지 않는다.
